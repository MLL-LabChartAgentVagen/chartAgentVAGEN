## 0 · 怎么读这份文件

**本文按流水线的顺序排。** 一步一节，每节里都是同样四块：

| | |
|---|---|
| **这一步做什么** | 输入、输出、内部机制 |
| **这一步的设计决定** | 为什么这么切，各对着一处会踩的坑 |
| **落在这一步的缺口** | ParseBench 上量出来的改动，就地展开，不另起一节 |
| **施工清单** | 这一步要勾的项 |

改动项带记号 `▸P9`（ParseBench 的十条缺口之一）或 `▸键的每段记来源`（那一条抬一层之后的一般化形式）。**没有记号的项是流水线本来就要写的东西**——ParseBench 是覆盖度的第一个对照集，不是这些设计的来源。

**一条不变式贯穿全文：ParseBench 是覆盖度的第一个对照集，不是目标函数。** 每条改动都写成一个带默认值、可枚举、可扫的维度，默认行为与今天逐位一致；换一把尺子时改的是对照集，不是流水线。

**做**：从领域池到训练目标文件的完整数据生成流水线，以及它的自检。
**不做**：模型训练、评测脚本、真实图表的抓取与清洗。这三项消费本流水线的产物，不在本仓库。
**规模目标**：16 种图表类型端到端可复现、单机能跑通。规模化只是重复调用，不是新设计。

## 1 · 总览

### 1.1 · 一条数据走完全程

五个阶段，一条单向的数据流。每个阶段只认它上游那一份数据接口。

```
配置 + 根种子
     │
     ▼
┌──────────┐ FactTable   ┌──────────┐            ┌──────────┐          ┌──────────┐          ┌──────────┐
│ 01 data  │+TableSchema │02 figure │ FigureSpec │03 render │RenderOut │04 record │  Record  │05 output │
│ 数据 LLM①│────────────▶│选图 LLM② │───────────▶│  渲染     │─────────▶│ 标注记录  │─────────▶│ 训练目标  │
└────┬─────┘             └────┬─────┘            └──────────┘          └──────────┘          └──────────┘
     │ 逐族判非空               │ 逐条判候选
     └──────────┬──────────────┘
                ▼
     registry/conditions.py    ViewSpec + TableSchema → 能不能画
     纯函数，01 与 02 共用，只读声明

──────────────────── 共享层（第 2 节）────────────────────
  interfaces/  六份数据接口，唯一定义处
  registry/    图表条件表 + 条件判定 + 可读性判据
  common/      种子 · 几何 · 像素反算 · 读写与版本 · 缓存
```

| 阶段 | 输入 → 输出 | LLM |
|---|---|---|
| [01 data](#3--01-数据) | 领域池 → FactTable + TableSchema（含场景与意图绑定） | **1 次**：写场景、生成脚本与意图绑定。解析、判族、执行、结构检查全是程序 |
| [02 figure](#4--02-选图) | FactTable + TableSchema → FigureSpec | **1 次**：选完图之后写标题与列的散文名。选图本身全是程序 |
| [03 render](#5--03-渲染) | FigureSpec + StyleVector → RenderOutput | 0 |
| [04 record](#6--04-标注记录) | RenderOutput → Record | 0 |
| [05 output](#7--05-输出) | Record → 训练目标文件 | 0 |

每个阶段是一个函数：`阶段(上游产物, 种子, 配置) -> 下游产物`。同样的输入必得同样的输出，产物按输入的内容哈希落盘。任何阶段可以单独重跑，也可以拿样例文件单独开发。

**没有候选清单这个中间产物。** 01 只判每个族非空还是空；02 的三类图分别用构造、推导、采样产出具体 ViewSpec。两处调同一个 `registry/conditions.py`。

### 1.2 · 两次 LLM 调用，都不产出数值

**整条流水线两次调用**：01 写数据（场景、脚本、意图），02 在图选定之后写字（标题与列的散文名）。03–05 全部由程序执行。

> **注意：这是本计划落地之后的形态。** 规格（`../storyline/parsebench_chart/README.md`）与仓库 `README.md` 现在写的仍是「只有一次 LLM 调用」——第二次调用是本计划新加的，由 [C6.7](#48--施工清单--c-组) 负责把两处一起改。为什么要加、边界在哪，见 [4.5 标题从哪来](#45--标题从哪来该加的第二次-llm-调用)。

**LLM 只在「定义」和「命名」时出现，不在「选择」时出现。** 01 定义场景、列、单位、可加性、有序性与意图绑定；02 在图已经选定之后给它们写标题与列名。构造、推导、采样、拒绝、组版全部是规则，每次运行可复现。

### 1.6 · 运行方式

**种子**：一个根种子，按 `(scenario_id, 阶段名, 序号)` 派生子种子。任何阶段不读全局随机状态。

**缓存**：每个阶段的产物按输入的内容哈希落盘，命中直接返回。改 03 不会触发 01–02 重跑，这同时就是断点续跑。

**产物布局**：`data/generated/<run_id>/<scenario_id>/` 下按阶段分文件，图像与记录同名不同后缀。

**产物自带可读视图**：写 schema 的同时写一份 `schema.md`（层级树、数值列依赖、意图指向三张 Mermaid 图，加可画族与最密叉积）。不用另跑命令才能看懂一次运行产出了什么。

**失败处理**：任何阶段失败只丢弃当前场景并写一条带原因的记录，不中断批次。跑完输出各阶段通过率——这是流水线健康度的主要观测量。

### 1.7 · 视觉出处：三条改动合起来是一件事

输出单位是「键 · 值 · 区域」。**这一轮改完之后，每一个原子都能回答一句话：你是从图上哪里、通过哪一种编码被读出来的。**

| 原子 | 出处字段 | 从哪几条来 |
|---|---|---|
| **值** | `value_axis`（对着哪条轴）＋ `mark_shape`（按哪种形状换算）＋ 可读判据的容差 | [P9](#p9--图元记下它对着哪条轴自己是什么形状) ＋ [P1](#p1--可读判据的容差从写死变成参数) |
| **键的每一段** | `KeySource`：轴刻度 / 图例 / 面板标题 / 图元旁标注 / 标题里 / 只有颜色 / 记号形状 / 填充纹理 / 没写 | [P2 ＋ P8 抬一层](#47--键的每一段记下角色与来源吸收-p2--p8) |
| **图外的每一段文字** | `TextBlock.role`：图号 / 主标题 / 副标题 / 单位 / 来源行 / 注释行 / 轴标题 / 图例标题 | [P7 抬一层](#56--图外文本是一等对象p7-的一般化) |
| **区域** | 边画边记——框在画的那一刻就写下来了 | 流水线本来就有 |

**急诊科例子上的一整句**：`("Mercy General", "Surgery")` 这一段里，`Mercy General` 读自面板标题、`Surgery` 读自 x 轴刻度；值 `42.3` 是拿矩形的上边对着左边那条值轴量出来的，容差 0.13 分钟；框是 `[168,196,278,520]`；单位 `minutes` 只写在副标题里。

**要不要跟某一条 P 合并**：不合并。它不是第十一条缺口，是这十条里三条各出三分之一拼出来的**那条轴**。合进任何一条，另外两条就会看起来像零碎的字段改动。它在文档里的位置就是这里——总览的一节；三条各自的正文仍在它们落的那一步。

**它换来什么**：真实图表的标注只能事后猜「这个数是从哪读出来的」，我们的记录在画的那一刻就写下来了。于是多出一类别人给不出的训练目标——「这一段名字是从哪读到的」「这个数是对着哪条轴量出来的」。而**寻址类错误占解析器失败的 72.2%**。

## 2 · 共享层：五步的地基，不是其中一步

**这一节不是流水线的一步**，是五步共用的地基：六份数据接口、图表条件表、公共模块。它排在最前面，是因为**接口不定死，后面五步没法并行开发，也没法写第二遍**。

十条缺口里有四条的本体落在这里（P9 · P1 · P10 · P5），另外五条在这里只占几个字段、正文在它们各自的那一步。

### 2.1 · 六份数据接口

**这一步在写任何阶段代码之前完成。** 接口定死之后，五个阶段可以并行开发：每个人只需要上游的样例文件。改接口要同时改样例文件并升 `schema_version`，让旧产物在读取时报错而不是静默错算。

| 接口 | 从 → 到 | 字段 |
|---|---|---|
| **FactTable** | 01 → 02 | 行级事件表，落盘为 parquet |
| **TableSchema** | 01 → 02 | 场景标题与数据背景、维度组与层级链、列清单（类型 / 所属组 / 父列 / 基数 / ordered；数值列另含单位与可加性）、依赖图、**意图绑定**（句子 + 目标列 + 聚合 + 族）、总行数 |
| **ViewSpec** | 02 内部 | 图表类型、列绑定、聚合、行过滤、求值结果、每组行数、逐行形态的抽样索引 |
| **FigureSpec** | 02 → 03 | 面板列表、版面、共享关系（含共享图例时的系列列）、多面板的关系类型、来源 |
| **StyleVector** | 03 内部 | 七组风格维度；随记录一起存，供消融按维度分组 |
| **RenderOutput** | 03 → 04 | 图像路径与尺寸、L0 元素、L1 面板 / 轴 / 图元 / 图例、施加过的退化变换 |
| **Record** | 04 → 05 | RenderOutput 拼上 L2 行数与逐图元的 `readable` |

**场景散文与意图绑定是 TableSchema 的字段**，与列声明在 01 的同一次调用里产出，不占单独的跨阶段产物。

三条约定：**键是有序字符串元组**（`("Mercy General", "Surgery")`，三层记录靠 `(figure_id, panel_id, key)` 对齐）；**框只有一种写法**（像素、原点左上、`[x0,y0,x1,y1]`，与图像宽高一起存）；**每个接口对象带 `schema_version`**。

以[急诊科示例](../storyline/parsebench_chart/README.md#贯穿示例)为例：

```
TableSchema   hospital(3)→department(4)、severity(3,ordinal)、visit_date(182天)
              wait_minutes minutes 可加 · cost USD 可加 · satisfaction points 不可加
              意图绑定 ①比较 hospital×AVG(wait) ②趋势 visit_date×AVG(wait) ③关系 wait×satisfaction
FactTable     900 行，一行一次就诊
FigureSpec    bar，x=hospital，y=AVG(wait_minutes)
              Mercy General 42.3 (372 行) · St. Luke's 35.8 (315 行) · Riverside 28.1 (213 行)
StyleVector   不写数值标注 · 企业蓝 · y 轴起点为零 · 900×600 · JPEG 75
RenderOutput  绘图区 [96,60,860,520]，y 值域 [0,60] ↔ 像素域 [520,60]；Mercy General的条 [168,196,278,520]
Record        上面这些 + rows=372 + readable=true
```

### 2.2 · 图表条件表是唯一定义处

新增一个图表类型只改 `registry/charts.py` 加一个绘制分支，不改 01、02、04、05 的任何代码。

**视觉变体归风格向量，不进类型表。** 四类条件、图元形状、值字典逐项相同的两个「类型」（实心饼与中空饼）只占一行。**但共享图例要求各面板共用系列列，这条是 FigureSpec 的硬约束，风格改不动**——不满足就退化成每面板一个图例，多面板图的主要价值消失。

### 2.3 · 像素反算只有一个实现

`common/readback.py` 提供「框内某颜色的占比」与「框 + 轴 → 值」。04 的自检拿渲染器的记录当输入，05 的可验证奖励拿模型输出当输入——**前两项自检只需要图像和被声称的「值 · 框」，不需要真值**，所以同一段代码在生成端是自检、在训练端是奖励。

### P9 · 图元记下它对着哪条轴、自己是什么形状

**这一条和定位用的键无关。** 键是 `record.Mark.key`，已经有了；P2 / P8 也不改它，只改导出时拼多长。这里加的是两个**读法**字段——一块像素要换算回一个数，得先知道照着哪条轴、按哪种形状换算。

一个面板里只有一个视图时，两者都能从 `Panel.chart_type` 推出来。它们成为新信息，是因为**一个面板可以有两条轴、两种图元**（见 [4.6 组合图](#46--组合图从类型表的一行改成一条组合规则)，以及 [P6](#p6--风格向量补取值) 的 `series_marks`）。

- `record.Mark` 加 `value_axis: AxisRole = "y"`（指向 `Panel.axes` 里的一条，`role` 在一个面板内唯一，不用另造 id）与 `mark_shape: MarkShape`
- `charts.ChartType` 的 `mark` / `channel` 从单值改成元组
- `common/readback.py` 反算时按 `value_axis` 取轴，不再默认取 `"y"`
- `record.Panel` 的 `chart_type: str` 改成 `chart_types: tuple[str, ...]`
- **不能靠现查**：导出器只读 `Record`，不该回去翻 FigureSpec（记录自足是接口的前提）

**下游**：03 每画一个图元写这两个字段（[D2.9](#5--03-渲染)）；04 反算时按 `value_axis` 取轴。

### P1 · 可读判据的容差，从写死变成参数

ε ＝ `value_per_pixel(value_range, pixel_range)`，两个输入**都已经在 `Panel.axes` 里**，用的时候现算。**不新增字段、不动接口、不抬版本。** 缺的只有一处：`channels.py` 把 1% 写死了。

- `channels.readable(channel, *, labeled, value, axis, tolerance)` 加一个参数
- `channels.tolerance(labeled, base)` 加一个参数
- 三个调用点各传各的，**不能互相替换**：

| 调用点 | 传什么 |
|---|---|
| `s05_output/export.py` 抽查标注集 | 基准口径：写了标注 0，估读 1% |
| `s04_record/selfcheck.py` 回读自检 | ε（这个比较今天没有阈值可用） |
| `s05_output/verify.py` RL 奖励 | 同上，一份实现 |

### P5 · 基数上界随密度档

### 2.7 · 类型表由乘积定义，缺口靠枚举找（P10 的一般化）

P10 的三行来自「这 100 页里出现过、我们没有」。**一族图只要没被抽到就进不了清单**。

类型表真正的定义是 **投影形态 × 图元形状** 的乘积。现在 13 个类型占 20 格里的 7 格：

|  | `rect` | `point` | `sector` | `cell` | `boxlike` |
|---|---|---|---|---|---|
| `grouped_scalar` | bar 族 · waterfall · funnel | line · area | pie | heatmap | — |
| `grouped_fivenum` | **空** | **空** | — | — | box |
| `binned_count` | histogram | — | — | **空** | — |
| `per_row` | **空** | scatter | — | — | — |

标粗的四格是**乘积预测出来、这 100 页没抽到**的：

| 空格 | 是什么 | 真实报告里常见吗 |
|---|---|---|
| `grouped_fivenum` × `rect` | 区间条 / 哑铃 | 是 —— 正是 P10 的第一行，**乘积自己预测到了** |
| `grouped_fivenum` × `point` | 误差棒 / 区间点图 | 是 |
| `per_row` × `rect` | 甘特 / 时间条（一行一个事件，起止两端） | 是 —— 这 100 页一张没抽到 |
| `binned_count` × `cell` | 二维分箱热力 / hexbin | 是 |

**改法**：把这张网格写进 `chart_types.md`，**每一格要么填一个类型，要么写明为什么空着**。加第六种图元形状（带状）就是多一列，四格候选一次性冒出来。

### 2.8 · 风格向量是一张声明式取值域表（P6 的一般化）

P6 的写法是「照实测清单补 30 项」。清单会过期，原则不会：**任何不改变答案的视觉决定，都必须是一个带取值域的可采样维度。**

**改法**：`STYLE_DOMAINS: dict[str, StyleDim]`，每维四个字段——取值域 · 默认 · 绘制分支 · **是否影响可读性**。配一条元测试：

- 每个声明的取值都有绘制分支（否则记录会写下一件没发生的事）
- 标了「不影响可读性」的维度，在自检③下答案逐位不变
- 覆盖度对照集**可替换**：今天是 ParseBench 的 65 项词表，换一份词表只换一个文件

这样「还缺哪些画法」是一句 `set(vocabulary) - set(STYLE_DOMAINS)`，不是一次人工比对。取值域填什么、每个取值配哪个绘制分支，见 [5.5 P6](#p6--风格向量补取值)。

**一行长什么样**：

```
STYLE_DOMAINS["value_labels"] = StyleDim(
    domain   = ("none", "all", "some", "outside", "outside_leader"),
    default  = "none",
    draws    = "s03_render/draw/rect.py::_write_label",
    readable = True,   # 印了数值的图元，容差降到 0
)
STYLE_DOMAINS["panel_bg"] = StyleDim(
    domain   = ("white", "tint", "grid_band"),
    default  = "white",
    draws    = "s03_render/draw/canvas.py::_panel",
    readable = False,  # 不改答案 ⇒ 自检③下逐位不变
)
```

`readable=True` 的维度改答案（印了数值就等于把值写在图上），`readable=False` 的不改。**元测试查的就是这一栏**：标了 `False` 的维度，换一档之后自检③读出来的键 → 值必须逐位相同。

**下游全部只认这两样**。场景散文与意图是 TableSchema 的字段，不是单独的产物。

### 3.1 · 一次调用写三段，不拆成两次

脚本是场景的形式化写法。分两次调用会在中间放一层有损的 JSON（层级、有序性、单位、可加性在自然语言里都不显式），而且下游没有回到上游的反馈通路。

**三段各有独立校验**：去重查场景、结构检查查脚本、绑定校验查意图；哪段不过就带具体原因回喂哪段。因为列与意图是一起写出来的，**意图绑定是构造出来的，不是事后推断的**。

### 3.2 · 可行性在声明期就判完

结构条件与语义条件只依赖列声明：`dim` 的取值表给出基数，`time` 的起止与频率给出点数，`additive` 与 `ordered`（`None` / `"ordinal"` / `"stage"`）是声明字段。**01 只问每个族是不是非空，从不展开组合。** 只有方差 / 相异值 / 实际单元格数要看真实数据。

### 3.3 · 原子粒度

一行事实表 ＝ 一次事件。聚合只发生在 02 的投影里，而且那里有三种形态根本不聚合。

### 落在这一步的缺口：只有一条

十条缺口没有一条以 01 为主体。唯一要动的是 [P5](#p5--基数上界随密度档) 的下游：**密度档给出行数下界**，事实表要跟得上，否则高密度档一开，`_allocate` 会把长尾压成 1 行而结构检查查不出来。

## 4 · 02 选图

**FactTable + TableSchema → FigureSpec。** 这一步决定这个场景出哪几张图、每张图画什么，然后（在图定下来之后）给这一批图写标题。

**这一步在急诊科例子上产出 8 张图**：

```
意图图（构造，3 张）  ① bar      hospital × AVG(wait)        ← 意图①比较
                      ② line     visit_date × AVG(wait)      ← 意图②趋势
                      ③ scatter  wait × satisfaction         ← 意图③关系
多面板图（推导，2 张）④ 2 面板   以①为锚点，正交切面：每个 panel 一家医院，x=department
                      ⑤ 2 面板   以②为锚点，时间对照：上半年 / 下半年
轮转图（采样，3 张）  ⑥ pie      department 占比
                      ⑦ box      hospital × wait 的五数
                      ⑧ heatmap  hospital × department
第二次 LLM 调用       8 张图的 schema 一次交上去 → 8 个标题 ＋ 每列的散文名
```

**冗余判据在这里挡掉了什么**：轮转时抽到过 `bar(hospital × AVG(cost))`——键集合与①相同（三家医院）、图元形状也相同（矩形），拒掉。抽到 `bar(department × AVG(wait))` 就收下：键集合不同。

### 4.1 · 三类图，三种产出方式，只有一种需要随机数

**没有 LLM 参与选图，也没有候选清单。**

| | 怎么产出 | 它的价值 |
|---|---|---|
| **意图图** | **构造**。绑定固定了列、聚合与族；条件表固定了类型；确定的顺序打破并列 | caption——只有意图图的说明里有图上读不到的信息 |
| **多面板图** | **推导**。锚点必须是一张已经单独通过准入的图（于是共享视图白给一个配对样本），另一个面板由关系规则算出来 | 版面形态本身；`applies_to_panels` 在单面板图上恒真，没有多面板图这个目标就永远是空的 |
| **轮转图** | **采样加拒绝**。逐族抽（类型、列、聚合），校验、投影、判进出，最多 T 次 | 覆盖度 |

**名字描述的是「这张图怎么被选中的」，不是它的重要性**——不要重新引入「主图 / 补充图」。

**不枚举候选清单。** 枚举要把几百到几千条候选全算出来、每条投影一遍才知道通不通过，而一个场景只出十来张图。

### 4.2 · 投影永远是一条 SELECT，四种形态

`project.py` 只有四条路径，按形态分支，不按图表类型分支：

| 形态 | 用在 | 特点 |
|---|---|---|
| 分组标量 | bar 族 · line · area · pie · heatmap · waterfall · funnel | 一组一个数 |
| 分组五数 | box（**区间条复用这一路**） | 一组五个数 |
| 分箱计数 | histogram | 先定箱边再计数，`rows` ＝ `count` |
| 逐行不分组 | scatter | 要按种子确定性下采样到类型的点数上限；L2 退化成每图元 1 行 |

聚合集合跟着形态走——`FIVE_NUM` / `BIN_COUNT` / `NONE` 不是 SUM/AVG/COUNT。四者分支，是因为值字典大小、能用哪些数据条件、L2 有没有用，三件事都不同。

**四种形态在急诊科数据上各投一次**（900 行事实表，一行一次就诊）：

```
分组标量   SELECT hospital, AVG(wait_minutes), COUNT(*) FROM t GROUP BY hospital
           → 3 个图元　("Mercy General",) {"value": 42.3}  rows=372
分组五数   SELECT department, 五数(wait_minutes)          FROM t GROUP BY department
           → 4 个图元　("Surgery",) {"min":8,"q1":22,"med":35,"q3":51,"max":97}  rows=210
分箱计数   先定 12 个箱边，再 SELECT bin, COUNT(*)         FROM t GROUP BY bin
           → 12 个图元　("30–35",) {"count":88,"bin_lo":30,"bin_hi":35}  rows=88
逐行不分组 SELECT wait_minutes, satisfaction              FROM t          （不 GROUP BY）
           → 900 行超过点数上限 400，按种子确定性抽 400 个图元
             ("row_00317",) {"x":38.0,"y":3.4}  rows=1
```

**这就是为什么必须按形态分支**：值字典从 1 个键到 5 个键不等，`rows` 的含义从「这一组有几行」变成「这一箱有几个」再变成恒等于 1，能用的数据条件也各不相同。

### 4.3 · 多样性由判据管，不由数量管

**批次里已经有一张「键集合相同、图元形状也相同」的图，就拒掉。** 没有阈值要调。

`K_max` 只是渲染与存储的预算。拿数量当多样性的代理挡不住「八张图全是 `bar(hospital × …)`」。判据取这一对，是因为输出单位是「键 · 值 · 区域」：键集合决定图上出现哪些实体，图元形状决定框长什么样、值字典有几个键、值能不能从像素读出。

**多面板图不受这条管**——键重复正是版面配对样本的来源。

### 4.4 · 行过滤只在 `panel.py` 里出现

它只服务「时间对照」一种关系，是配对时从锚点现场切出来的，不是 ViewSpec 的一个采样维度。

### 4.5 · 标题从哪来：该加的第二次 LLM 调用

**一条规则：02 选完图之后，把这一批图的 schema 一次交给 LLM，每张图回一个标题。** 不分意图图和其余的图。

**为什么不分**：意图那个区分是 **caption** 的事，不是标题的事。caption 是训练目标里的一段文字，讲图上读不出来的信息，所以意图图有意图可用、别的图没有。标题块是**画在图上的字**，每张图都得有。两件事，两条规则，不该互相牵连。

**为什么不能拼模板**：一个场景 8 张图，01 只写 3 条意图。要是 3 张用意图写标题、5 张拼模板，语料里就有**两种一眼看得出的标题腔调**，模型会学到「模板腔 ＝ 这一类图」——这是我们自己造出来的假信号。而且模板标题（`Average wait time by hospital`）**从坐标轴就能猜出来**，[P7](#p7--标题块成为记录里的对象含面板小标题) 想立的点是「单位只写在标题里」，标题一可猜，这个点就废了。

怎么调：

| | |
|---|---|
| 什么时候 | 02 选完图之后、03 开画之前 |
| 调几次 | **一个场景一次**，8 张图批在同一次调用里。不是一张图一次 |
| 给它什么 | 场景散文 ＋ 每张图的（类型、列、聚合、单位、面板名、关系）。**不给任何数据值** |
| 它回什么 | 每张图的主标题 / 副标题 / 单位，外加**每列的散文名**——轴标题和图例也要用，不然轴上写的是 `wait_minutes` |
| 校验 | **不许含数字**（年份与单位除外）。标题画出来就是真值，一句「等待时间大幅下降」会污染后面导出的问答对 |
| 缓存 | 按内容哈希，与 01 同一套 ⇒ 同一份输入必得同一批标题 |
| 拿不到模型时 | 退回模板。**这是给离线开发和 e2e 测试的兜底，不是一个可选档** |
| 落点 | `s02_figure/title.py`，在 `compose.py` 末尾调用 |

**这一次调用长什么样**（急诊科场景，8 张图批在一起）：

```
给它  场景散文：「三家社区医院的急诊科…」
      图1  bar   x=hospital  y=AVG(wait_minutes) 单位 minutes  来源=意图「比较各院等待」
      图4  两面板 overlay  panel=hospital  x=department  y1=COUNT  y2=AVG(wait_minutes)
      …（共 8 条，一个数据值都没有）

回来  图1  主标题「Emergency department wait times by hospital」
           副标题「Average per visit, Jan–Jun 2024」　单位「minutes」
      图4  主标题「Visit volume and average wait, by department」
           副标题「Each panel is one hospital」　　　　单位「visits · minutes」
      列名 wait_minutes → "Average wait"　cost → "Cost per visit"
           satisfaction → "Patient satisfaction"　department → "Department"
```

**列的散文名是必须要的那一半**：没有它，轴上写的是 `wait_minutes`、图例里写的是 `severity`。这两处的字**同时是键的来源**（[4.7](#47--键的每一段记下角色与来源吸收-p2--p8) 里的 `axis_tick` 与 `legend`），所以它们是不是人话，直接决定这张图的键能不能被逐字复制出来。

**校验拦掉的是这种**：`Wait times fell sharply after triage reform` —— 画出来就成了图上的真值，而数据里并没有这回事。规则是**不许含数字**（年份与单位除外）＋ 只许命名画了什么，不许陈述结论。

**代价：整条流水线从一次调用变成两次。** 这是规格里白纸黑字的一条不变式，要一起改（见 [9.4](#94--规格同步)）。

**但改的只是「几次调用」。** 那条更深的约束没动——第二次调用不判可行性、不选图、不产生任何值 / 键 / 框，它的输出全部落在画出来的文字里。

### 4.6 · 组合图：从类型表的一行，改成一条组合规则

不占 P 编号，但它是这一轮唯一一处结构改动，**做在 [P9](#p9--图元记下它对着哪条轴自己是什么形状) 之后**。

现在 `charts.py` 里有一行 `compound`，写死了「恰好一个分组列、恰好两个测度、一个系列、矩形 ＋ 点、两条纵轴」。两个问题：

| | 核实 |
|---|---|
| **今天根本选不出来** | 那一行 `family=None`，轮转按族抽、`in_family()` 按 `family` 过滤 ⇒ 它不落在任何一族里。是一行谁也够不着的死行 |
| **写死的那一对是任意的** | `02_figure.md §4.1` 的「双指标」关系写的是「同面板双轴 compound，**或**并排共享 x 轴」——同一条关系，落在一个绘图区叫 compound，落在两个绘图区叫多面板图。那它是一种**版面**，不是一种类型 |

**同一个绘图区可以放不止一个视图。** 多面板图是「两个视图、两个绘图区」，组合图是「两个视图、一个绘图区」。同一条关系，两种落法。

改法：挪到多面板图旁边，用同一种机制。

- `registry/charts.py` **删掉 `compound` 那一行**
- `interfaces/figure.py`：`PanelSpec.view: ViewSpec` → `views: tuple[ViewSpec, ...]`（长度 1 就是今天的行为）；`Layout` 的 `"dual_axis"` 改成 `"overlay"`——叠加不一定双轴，**实测 59 个组合图里 39 个只有一条值轴**，轴数由量纲决定，不该写进版面名
- `s02_figure/panel.py` 加一条组合规则，与五种多面板关系并列。**组合图和多面板图一样是「推导」出来的，不采样**——从一张已经通过准入的锚点图出发，规则算出第二个视图。三条叠加语义、选列打分与乘积表见下面三小节
- `s02_figure/project.py`：一个面板可能要投影不止一次，每个视图各一次
- **冗余判据不用改**——判据是「键集合 ＋ 图元形状」，组合图的形状集合 `{rect, point}` 与普通条形的 `{rect}` 天然不同
- **01 的 LLM 契约不用改**——`compound` 本来就 `family=None`，从来没进过覆盖度检查

> **实测对得上。** 三家在 100 页上标出 59 个组合图（30 页），叠加形态证据 79 条：点 / 菱形 / 三角 54 · 折线 29 · 短竖线 9 · **底层是堆叠条 14** · 带状 7。写死那一行只覆盖「bar ＋ line ＋ 双轴」一种；改成组合规则之后，除带状（等 P10 引入带状图元）之外全都能画。
> **一件容易误会的事**：「折线叠在条上」与「菱形叠在条上」在我们的形状分类里是**同一种组合**——`line` 与 `scatter` 都写着 `mark="point"`。点连不连线、画成什么记号是 P6 的 `series_marks`，不是两种图。

#### 谁跟谁叠：三条语义

「组合图」不是一种搭配，是**两个视图共用一个绘图区**这件事的三种理由。三条都从锚点推导，都不需要随机数。

| | 两个视图的关系 | 急诊科例子 | 前提 |
|---|---|---|---|
| **语义一 · 两个测度** | 同一批键，两个不同的数值列 | 各科室的**就诊量**（条）＋**平均等待**（线） | 现在就能做 |
| **语义二 · 同一测度的两次切片** | 同一批键、同一列，两个行过滤或两个聚合 | 各科室**上半年**（条）＋**下半年**（点）；各科室**平均**（条）＋**九十分位**（点） | 行过滤从「时间对照」那条关系借现成的 |
| **语义三 · 值加它的区间** | 同一批键、同一列，一次分组标量 ＋ 一次分组五数 | 各科室**平均等待**（条）＋**最短–最长**（带） | 要等 [P10](#p10--类型表加三行) 把带状图元引进来 |

**只写语义一，就把 `compound` 那一行的毛病换个地方犯了**——写死一种搭配。三条语义覆盖实测里的三类：79 条叠加形态证据里，点 / 菱形 / 三角 54 条大多是语义一或二，带状 7 条是语义三。

#### 语义一怎么选第二列（确定顺序，没有随机数）

锚点固定了分组键 `K`、第一测度 `m1`、聚合 `a1`。第二测度 `m2` 从 `TableSchema` 的数值列里选，**按下面的顺序取第一个可用的**：

| 顺位 | 挑什么 | 为什么排在这 | 急诊科例子 |
|---|---|---|---|
| 1 | **依赖图上与 `m1` 有边**的列 | 「一个量和它的派生量」是报告里最常见的双指标 | `cost` 由 `wait_minutes` 算出来 |
| 2 | **可加性与 `m1` 不同**的列 | 可加的量当底图（矩形，从零起算），不可加的率或评分当叠加（点 / 线）——就是「总量 ＋ 比率」那种最常见的报告图 | 就诊量（可加）＋ 满意度（不可加） |
| 3 | **量纲与 `m1` 不同**的列 | 不同量纲才需要第二条轴；同量纲的一对更适合 `grouped_bar`，本来也会被冗余判据挡掉一部分 | minutes ＋ USD |
| 4 | 列清单里的下一个 | 兜底 | — |

- **聚合 `a2` 不用挑**：由 `m2` 的可加性定——可加 → SUM，不可加 → AVG。与规格里数值列的聚合规则同一条
- **谁当底图**：可加、从零起算的那个（矩形）。两个都可加就按列清单顺序取前一个
- **一个都选不出来就不出组合图**，记原因，不降级成别的形态

#### 轴数由量纲定，不由版面名定

| 情形 | 几条值轴 |
|---|---|
| 同量纲 | 一条 |
| 异量纲 | 两条 |
| **同量纲、但两个值域比 > 20 倍** | **也给两条** |

第三行是必须写的：不给第二条轴，叠加那条线会压成贴着轴的一条直线，值读不出来，**自检②会把整张图丢掉**。同量纲且值域相当时，一条还是两条由 [P6](#p6--风格向量补取值) 的 `dual_axis` 采样决定。

#### 乘积：底图 × 叠加

**合法条件 ＝ 各视图各自过自己那一行 ∧ 分组键相同 ∧ 图元形状不同。** 第三项把格子筛掉一批：

| 底图 | 图元 | 能配的叠加 | 格数 |
|---|---|---|---|
| `bar` · `grouped_bar` · `stacked_bar` · `waterfall` · 区间条 | 矩形 | `line` · `scatter` · windsock | 5 × 3 ＝ **15** |
| `area` | 点 | 只有 windsock（`line` / `scatter` 也是点，形状相同不合法） | **1** |

**16 格**。其中含 windsock 的 6 格要等带状图元，所以**现在能画 10 格，[P10](#p10--类型表加三行) 落地后 16 格**——写死那一行只有 1 格。

> **`area` 那一格容易看错**：`line` · `area` · `scatter` 三个都写着 `mark="point"`，所以「折线叠在面积图上」在我们的形状分类里是两个相同形状叠在一起，不合法，也确实分不开——两批图元的框重合，`mark_shape` 也一样，记录里没法把它们分开。

### 4.7 · 键的每一段记下角色与来源（吸收 P2 ＋ P8）

`Mark.key` 现在是一个有序字符串元组，**没有角色、没有来源**。而 ParseBench 的分析契约里每一段键都带 `(role, label_source)`——这一轮 100 页量到 924 段：

| 角色 \ 来源 | `axis_tick` | `legend` | `panel_title` | `inline_label` | `heading` | `colour_only` | `not_shown` |
|---|---|---|---|---|---|---|---|
| `category` | **224** | | | 30 | | | |
| `time` | **178** | | | | | | |
| `series` | | **298** | | 28 | 12 | | 3 |
| `panel` | | | **84** | 8 | 14 | | |

**[P2](#p2--面板名进对外的键) 与 [P8](#p8--颜色分组进对外的键) 是这张表里的两格**——`panel` 那一行、`colour_group` 那一行。把它们各写成一条特例，就永远拿不到另外三格：

- `inline_label` **72 次**：名字直接标在图元旁边，不在轴上也不在图例里。今天我们一个都画不出来
- `heading` **28 次**：名字只写在图的标题里（「Figure 3 · Mercy General」）
- `not_shown` 7 次：页面上根本没写，键不可从图上复原——这类点应当**主动排除出值目标**

**改法**：`Binding` 的分组列各带一个 `KeySource`（`axis_tick` / `legend` / `panel_title` / `inline_label` / `heading` / `colour_only` / `mark_shape` / `hatch` / `not_shown`）。**02 按规则给每个分组列定这个值**，03 按来源决定这段名字画在哪，04 把 `not_shown` 的键排除出值目标，05 多出一类训练目标。

**这一条直接落在我们的可防守轴上**：不只是「键 · 值 · 区域」有出处，**键的每一段各有出处**。它同时给出一类新的训练目标——「这一段名字是从哪读到的」，而这正是解析器失败的大头（寻址类错误占 72.2%）。

#### 一张图上的四段键，四个出处

急诊科那张两面板图：面板标题写医院，x 轴刻度写科室，图例写分诊等级，其中一根条旁边直接印了 `Severe 61.4`。同一张图里四段键、四个来源：

```
FigureSpec.binding
  panel        = hospital     KeySource = panel_title    面板上方那行「Mercy General」
  category     = department   KeySource = axis_tick      x 轴刻度「Surgery」
  series       = severity     KeySource = legend         图例「Severe」
  colour_group = severity     KeySource = colour_only    只有颜色，图例里没有文字

Record.Mark
  key      = ("Mercy General", "Surgery", "Severe")
  key_src  = ("panel_title",   "axis_tick", "legend")
  values   = {"value": 61.4}
  box      = [412, 118, 448, 306]
```

**为什么必须逐段记，而不是整条记一个来源**：这一条键里三段的出处各不相同。模型要从图上把 `Mercy General` 找出来，得去看面板标题；要把 `Surgery` 找出来，得去看 x 轴刻度。**记一个「这张图的键来自哪」没有用**——它答不出这两个问题里的任何一个。

**同一份数据换个画法，来源就变了**：把两面板拆成一张图、医院进图例，那么 `Mercy General` 的来源就从 `panel_title` 变成 `legend`；把它改成一页两图、医院只写在图的标题里，就变成 `heading`。**键没变，出处变了**——这正是要单独记一栏的原因。

## 5 · 03 渲染

**FigureSpec + StyleVector → RenderOutput。** 画图，同时把每个部件的框、键、值记下来。**改动最密的一组。**

**画第①张图的那一刻，记下来的是这些**：

```
画布      900 × 600，dpi 100，绘图区 [96, 60, 860, 520]　← 三项写死，画完不许动
轴        y 值域 [0, 60] ↔ 像素域 [520, 60]　x 类目轴 3 格
画第一根条 rect(x=168, y=196, w=110, h=324)
          ——同一行写下 Mark(key=("Mercy General",), values={"value": 42.3},
                              box=[168,196,278,520], value_axis="y", mark_shape="rect")
文本块    Figure 3 / 主标题 / 副标题 / 单位　占固定高度，有没有标题都留着
```

**为什么框和值必须此刻一起写**：只有画这一笔的时候，`42.3` 与 `[168,196,278,520]` 两者同时在手。画完再回头解析图像，就得靠猜。

### 5.1 · 画和记不分开

画每个图元的那一行同时写记录——只有那一刻框、键、值三者同时在手。**永远不要先画完再回头解析图像。**

配套的硬约束是**布局参数冻结**：图像尺寸、dpi、绘图区矩形三项写死。自动布局会在画完之后挪动绘图区，把已经记下的每一个框静默作废。

### 5.2 · 按图元形状分文件，不按图表类型分文件

16 种类型只有 6 种图元形状。`draw/rect.py` 同时服务 bar 族、histogram、waterfall、funnel、区间条——差别只在值字典里填哪几个键。

### 5.3 · 风格向量在这里采样

逐维独立采样，随记录落盘，供消融按维度分组。**同一份 FigureSpec 渲两份风格版本**是一个产物，不是一次重试——自检③（换风格答案不变）的输入就是它。

数字格式受单位约束：百分号只给份额单位，货币符号取自单位，**标注文本永远是记录下来的那个数**。

### P7 · 标题块成为记录里的对象（含面板小标题）

真实页面的标题块在绘图区**外面**，可能在上、在下、在侧，可能属于整张图，也可能是**每个面板上方的一个小标题**（三家一致 24 页）。

- `interfaces/figure.py` 加 `TitleBlock(number, main, subtitle, unit, placement, scope)`，`scope ∈ {"figure", "panel"}`。一般化形式见 [5.6](#56--图外文本是一等对象p7-的一般化)
- `FigureSpec` 与 `PanelSpec` 各挂一个可选 `title`
- `interfaces/record.py` 的 `Element` 加 `text: str`——**画出来的那串字才是真值**，不是 FigureSpec 里的字段
- `main` / `subtitle` / `unit` 的内容由 [4.5 的那次调用](#45--标题从哪来该加的第二次-llm-调用)给出；只有 `number` 是新信息（页面合成时才编）
- **标题块占固定高度，有没有标题都留着**（布局参数冻结是不变式 6）⇒ 绘图区矩形不随标题变
- **一次重算 ER 数字链**：`[96,60,860,520]`、`[168,196,278,520]` 在 `01`–`05` 五份文档里链住，绘图区下移就全失效

### P6 · 风格向量补取值

`interfaces/style.py` 的七组维度各自补取值域。这一轮实测缺 30 项，绝大多数**只加取值**，头部是：单位位置 · 负值与零线 · 值轴标题写在轴正上方 · 脚注上标 · 单类目高亮 · 非 ISO 时间刻度 · 数值标签在图元外 · 说明框 · 面板底色 · 横向条 · 图例画在绘图区内 · 系列名标在线旁 · x 轴两级标签 · 类目名折行。写法上要按 [2.8 的取值域表](#28--风格向量是一张声明式取值域表p6-的一般化)组织。

**两个新字段**，一个字段同时覆盖两处形态：

- `StyleVector.series_marks: tuple[MarkShape, ...] | None`——每个系列画成什么记号（连线 / 圆点 / 菱形 / 三角 / 短竖线）。默认 `None` ＝ 各系列都用类型自己的图元。覆盖 P9 那 22 页「同一条轴上两个系列换形状」，以及组合图的 92 条「菱形 / 折线 / 短竖线叠在条上」
- **边界**：`series_marks` 只许在**可测量的图元形状之间**换（矩形 / 点 / 带状）。换成扇形或格子会改变可读性，那就不再是「换风格答案不变」
- `StyleVector.dual_axis: bool`——一条值轴还是两条。两测度**同量纲时可选**，不同量纲时强制为真。实测 39 / 59 的组合图只有一条值轴
- 横条 / 竖条是**风格维度**（四类条件逐格相同），代价是 `rect.py` 要同时处理两个方向
- **每加一个取值同时加绘制分支**，并加一条自检——`style.py::sample()` 逐维独立采样，没有分支落实的维度会在记录里写下没发生的事
- **面板底色要先修 `readback.ink_fraction`**：它按白底判「框里有没有东西」，加底色后**静默失效**（自检恒过、偏移的框照样写盘）

### 5.6 · 图外文本是一等对象（P7 的一般化）

P7 的写法是「标题拆成图号 / 主标题 / 副标题 / 单位 / 位置」。同一个结构还能装下报告里另外几种图外文本，而报告分析把它们标成了「不进清单」——**理由是基准不看，不是我们不需要**：

| 角色 | 实测 | 报告归在哪 |
|---|---|---|
| 图号 · 主标题 · 副标题 · 单位 | P7 的四个字段 | P7 |
| **来源行 · 注释行** | 三家一致 **17 页**，这批页面里最常见的构造 | 「不进清单」 |
| 轴标题 · 图例标题 | 竖排轴标题 28 页 | 散在 P6 |

**改法**：`TextBlock(role, scope, placement, text)`，`role ∈ {figure_number, title, subtitle, unit, source, note, axis_title, legend_title}`，`scope ∈ {page, figure, panel}`。**一个类，八个取值**，比一个 `TitleBlock` 加几条散落的风格维干净。

配套：`record.Element` 的 `ElementCategory` 与 `TextBlock.role` 用同一份取值——画出来的字与它的角色一起进 L0，页面元素框目标因此不再是「五类粗标签」。


**一张真实报告页上的七块文字**，全用同一个类装：

```
TextBlock(role="figure_number", scope="figure", placement="above",  text="Figure 3")
TextBlock(role="title",         scope="figure", placement="above",  text="Emergency department wait times by hospital")
TextBlock(role="subtitle",      scope="figure", placement="above",  text="Average per visit, Jan–Jun 2024")
TextBlock(role="unit",          scope="figure", placement="above",  text="minutes")
TextBlock(role="axis_title",    scope="panel",  placement="left",   text="Average wait")     竖排
TextBlock(role="source",        scope="figure", placement="below",  text="Source: hospital admissions register")
TextBlock(role="note",          scope="figure", placement="below",  text="Excludes visits ending in transfer")
```

**记录里存的是画出来的那串字，不是 FigureSpec 里的字段**——两者可能不同（折行、截断、加了上标）。`Element.text` 存前者。

**来源行与注释行为什么值得装进来**：它们是这批页面里最常见的构造（三家一致 17 页），而且**只有它们能回答「这张图的数是哪来的」**。报告分析把它们标成「不进清单」，理由是基准不看——不是我们不需要。

## 6 · 04 标注记录

**RenderOutput → Record。** 三层拼接、逐图元判可读、三项自检。这一步不画任何东西，也不改任何框。

**这一步到底在干什么**：03 交上来的是「图像 ＋ 一堆记录」，04 给这堆记录**加上两个判断**——这个值读不读得出来、记的对不对——然后把三层拼成一行。

```
① 拼三层   L0 元素（文本块与它的框）
            L1 图元（("Mercy General",) → 42.3 → [168,196,278,520]）
            L2 行数（这一组由 372 行事实表聚合而来）
            靠 (figure_id, panel_id, key) 对齐 → 一行完整记录

② 判可读   ①号图的条是「长度」通道 ⇒ 可能可读，再看像素高度够不够 → readable=true
            ⑥号饼图的扇形是「角度」通道 ⇒ 不可读
            ——读不出来的图元掉出「值目标」，但仍留在「定位目标」里

③ 三项自检 框里有东西吗？        框内非底色像素占 63%              ✓
            量出来对不对？        (520-196) × 60/460 = 42.25
                                  与记录的 42.3 差 0.05 < ε = 0.13   ✓
            换风格答案变不变？    横向条那一版读出来还是 42.3        ✓
            —— 任何一项不过，整张图丢掉并记原因
```

**ε 是现算的**：`value_per_pixel(值域 60, 像素域 460) = 0.13 分钟`，两个输入都已经在 `Panel.axes` 里。这就是 [P1](#p1--可读判据的容差从写死变成参数) 说的「容差不该写死成 1%」。

**前两项自检不需要真值**——只要图像和被声称的「值 · 框」。所以同一段代码在生成端是自检，在训练端就是可验证奖励。

### 6.1 · 可读性在渲染之后判，判据只有一处

从实际像素几何加编码通道判：长度 / 位置类 → 可能可读；角度 / 面积 / 颜色类 → 不可读。规则只在 `chart_types.md §4` 定义一次。

**读不出来的图元掉出值目标，但仍留在定位目标里。**

### 6.2 · 三项自检在生产路径上，前两项同时是强化学习奖励

| | 查什么 | 需要真值吗 |
|---|---|---|
| ① | 框里有没有东西 | 不需要 |
| ② | 从像素反算出来的值与记录的值对不对得上 | 不需要 |
| ③ | 换一套风格，答案变不变 | 需要（拿两份风格版本比） |

失败就丢图并记原因。**每张图都跑，不放在测试里**——边画边记的错误只会在真实数据上暴露。

前两项只需要图像和被声称的「值 · 框」，所以 05 的可验证奖励调的是同一个 `common/readback.py`。第三项不需要额外渲染——它消费的两份风格版本本身就是一个产物。

### 落在这一步的缺口

| 缺口 | 这一步要做的 |

| [P1](#p1--可读判据的容差从写死变成参数) | 自检②的容差传 ε ＝ `value_per_pixel(*axis)`；抽查标注集那一路传基准口径（0 / 1%）；阈值取「容差」与「半个记录精度」的较大者 |

## 7 · 05 输出

**Record → 训练目标文件。** 八类训练目标 ＋ 可验证奖励。**对外产物的形状是导出参数，不是记录结构**——这一节的两个缺口都是这句话的实例。

**同一行记录，导成六样东西**：

```
记录     key=("Mercy General",)  value=42.3  box=[168,196,278,520]  rows=372  readable=true

带位置的表  | Mercy General | 42.3 | [168,196,278,520] |
抽查标注集  问「Mercy General 是多少」→ 答 42.3（容差用基准口径：没印数值，1%）
图元定位    问「Mercy General 那根条在哪」→ 答 [168,196,278,520]
图元读值    给框 [168,196,278,520] → 答 42.3
下钻        问「这个数由多少行原始记录聚合而来」→ 答 372
页面元素框  Figure 3 的标题块 [96,24,540,44]，按 page_id 与同页的图 4 合并去重
```

**`key_scope` 三档改的只是第一列**：

```
key_scope="mark"    ("Mercy General",)
key_scope="panel"   ("Mercy General", "Surgery")            ← 面板名进来了
key_scope="full"    ("Mercy General", "Surgery", "Severe")  ← 颜色分组也进来了
```

**一个字段都不用往记录里加**——`panel_id` 本来就在三层的连接键里，分色列本来就在 `Binding` 里。改的是导出时拼多长，而且这个选择**随产物落盘**，否则模型输出的键回落不到图元。

### 7.1 · 八类训练目标

A 组（带位置的表、抽查标注集）· B 组（图元定位、图元读值、下钻）· C 组（页面元素框、图例绑定）· caption。

导出程序只 import `interfaces/record.py` 与 `common/`，不 import 任何阶段模块——**记录自足**是接口的前提。

### P2 · 面板名进对外的键

**不改记录结构**：`panel_id` 已经在三层的连接键里。缺的只是「导出给模型的键要不要带上它」。

- `s05_output/export.py` 加导出参数 `key_scope`（与 P8 同一个参数）
- **面板名取自它自己的 `TitleBlock.main`**，所以「键必须逐字可复制」是白给的
- 面板没有标题块就**不许**把面板维算进键
- `key_scope` **随产物落盘**——不变式 11 要求模型输出的键能回落到图元，不知道用的哪个作用域就回落不了

### P8 · 颜色分组进对外的键

- `interfaces/figure.py` 的 `Binding` 加 `colour_group: str | None`（哪一列分色）。一般化形式见 [4.7](#47--键的每一段记下角色与来源吸收-p2--p8)
- `s05_output/export.py` 的 `key_scope` 决定附不附这一段
- **分色列归 `FigureSpec`，色值归 `StyleVector`。** 风格向量不能选哪一列分色，否则换风格就改 key，自检③（换风格答案不变）失效

### P3 · 一页多张图的时候，导出的表要分得开

一页多图 `03_render.md §5` 规格已有（「单页多图、跨栏、图注与图表分开这些真实版面现象，且可控」），只是 `page.py` 没写；标题块拆字段与位置是 [P7](#p7--标题块成为记录里的对象含面板小标题)。剩下三件真的：

- `s05_output/export.py` 加一个导出函数：**整页 markdown**——一页里每张图各成一张长表，图号与标题写成表**前面**的小标题。一般化形式见 [7.5](#75--导出粒度是一个参数p3-的一般化)
- 页面元素框目标**按 `page_id` 合并去重**再导出（一页两图各导一份会互相漏标对方的标题块）
- `s02_figure/admit.py` 的冗余判据给**同一页且标题块不同**的多张图开豁免（落在 [02](#落在这一步的另外一条同页豁免)）

### 7.5 · 导出粒度是一个参数（P3 的一般化）

P3 的写法是「加一个整页 markdown 导出函数」。一般形式是**导出粒度**：一图一表 / 一页一份 / 一批一份。加一个函数只解决今天这一种版面；一个参数把三种都覆盖，而且与 `key_scope` 是同一类东西。


同一页两张图（图 3 各医院等待、图 4 各科室占比），三档导出出来的东西：

```
granularity="figure"   两个文件。每个文件一张长表，不知道页面上还有另一张图
granularity="page"     一个文件。图号与标题写成表前面的小标题：

                       ## Figure 3 · Emergency department wait times by hospital
                       | key | value | box |
                       | Mercy General | 42.3 | [168,196,278,520] |
                       …
                       ## Figure 4 · Share of visits by department
                       | key | value | box |
                       | Surgery | 23.3% | [612,180,690,258] |

granularity="batch"    一个文件装一整批，训练时按 page_id 切
```

**`page` 档不是把两个文件拼起来**：页面元素框那一类目标要**按 `page_id` 合并去重**，否则两份各自只标了自己那张图的标题块，互相把对方的漏掉。

### 9.2 · 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 坐标漂移 | 自动布局、dpi、`bbox_inches` 改变实际绘图区，框整体偏移且不报错 | 冻结这三项；自检①逐图元拦截 |
| 轴映射错误 | 对数轴、负值、堆叠基线上反算出的值与记录的值不符 | 自检②；对数轴放到 Tier 1 之后再开 |
| 声明期与执行后基数不一致 | 按声明判非空的族在实际数据上一张也画不出 | 01 的结构检查强制实际基数与声明一致 |
| 单次调用负担过重 | 场景 + 脚本 + 意图三段一起写，某一段质量下降 | 三段各有独立校验，哪段不过就带具体原因回喂哪段 |
| 脚本失败率 | LLM 写的生成程序反复触发同一类异常 | 统计异常类型分布；高频类型进提示词的约束段，不靠加大重试次数 |
| 采样抽不中 | 某个族反复抽到不合法或冗余的候选 | 每族至多 T 次，超了就跳过并记日志 |
| 值目标稀疏 | 饼图、热力图的值几乎全部读不出 | 预期结果不是缺陷；值目标产出率按图表类型分别统计 |
| 风格泄漏进真值 | 某个风格参数意外改了求值结果 | 自检③按图抽样跑，输入就是风格配对样本 |
| 接口漂移 | 上下游对同一个字段的理解不一致 | 接口先定死；每份带版本号与样例文件；改接口必须同时改样例 |
| **标题对数值下断言** | LLM 写的标题说「等待时间大幅下降」而数据并非如此，这句话画出来就成了真值 | 校验拒绝含数字的输出；标题只许命名画了什么，不许陈述结论 |
| **第二次调用让流水线不再确定** | 同一份输入两次运行出不同标题 | 按内容哈希缓存，与 01 同一套；`tests/e2e/` 逐字比对 |
| 密度一开可读率坍塌 | 高密度档大批图元掉出值目标 | 是设计后果。`chart_types.md §4` 给出每档预期可读率 |
| 密度一开行数不够 | `_allocate` 把长尾压成 1 行且结构检查查不出 | 档位给行数下界，不够就降档 |
| 面板底色静默关掉自检① | 自检恒过、偏移的框照样写盘 | 先修 `ink_fraction`（A6.16，在 P6 之前） |
| `>400` 图元时标签渲染跑不动 | 每个标签一次全图重绘 | 先改 `_write_label`（D2.4，在 P5 之前） |
| 权重按下标写会静默错位 | 新增类型之后配比对错族 | 按名键入，随产物落盘 |
| 一页两图各导一份 L0 会互相漏标 | 两份都只标了自己那张的文本块 | 页面元素框按 `page_id` 合并去重 |
| 逐 value key 的回读自检扩大丢图面 | histogram 的 `bin_lo`/`bin_hi` 把 `bar_width` 钉死 | 只对有几何锚点的键做 |
| 标题块占高度让 ER 数字链失效 | 五份文档里链住的框全错 | 固定高度 ＋ 五份文档一次重算 |

### 9.3 · 验收

| | 怎么验 |
|---|---|
| 接口 | `tests/samples/` 往返逐位相同；`SCHEMA_VERSION` 3 读不了 2 的产物 |
| 组合图 | 三条叠加语义各生成一批：两个测度（`bar ＋ line`）· 同一测度两次切片（`bar ＋ 点`）· 值加区间（`bar ＋ 带`）；记录能靠 `mark_shape` 把两批图元分开；16 格乘积里每一格要么能生成，要么写明为什么不合法 |
| 键 | 多面板图与含颜色分组的图，导出的表里那两段独立成列；`KeySource` 五种来源各能产出样本 |
| 可读 | 饼图在 5% 容差下的去留算得出；不印数值的图上回读自检能判对错 |
| 标题 | 图号由页面合成器编；单位与基期从标题里拆得出来；caption 不含图上可读的信息；**标题里没有一个数值断言**；同一份输入两次运行标题逐字相同 |
| 类型 | 16 型都能生成；覆盖网格里每一格要么有类型要么写明为什么空 |
| 密度 | 五档都能生成，各档读数正确率与预期可读率对得上 |
| 权重 | 三档预设各生成一批，同种子逐位可复现；`uniform` 与改造前逐位一致 |
| 风格 | 每个声明的取值都有绘制分支；标了「不影响可读性」的维度在自检③下答案不变 |
| 导出 | 并排两张共用类目名的图，导出后不撞车 |
| 端到端 | `(输入, 种子) -> 输出` 逐位可复现；各阶段通过率进日志 |
| 对齐 | 用官方 `ChartDataPointRule` 在 568 页上自评，改造前后各一次 |
