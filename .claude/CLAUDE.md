# CLAUDE.md

## Project

Chart data generation for **grounded transcription**: synthesize charts where every rendered value carries the pixel box it was drawn in. Output unit is `(key, value, box)`. Ground truth is recorded while drawing — never obtained by annotating finished images.

- Spec: `storyline/parsebench_chart/` — the single source of truth.
- **All code is English** — comments, docstrings, exception text, prompts, CLI output. So is all pipeline-produced content: column values, units, scenario prose, intent sentences, captions, axis labels, slides. Chinese stays in the documents: `storyline/`, `README.md`, `plan/`.
- **Docstrings stand on their own.** Never refer to a stage by its number alone or to a spec section by number (`03 → 04`, `§4`, `L1`); say what the thing does and name the component. A spec path may follow as a pointer, never as the explanation. The running example is a US emergency department.
- What can be drawn and under what conditions: `storyline/parsebench_chart/chart_types.md`.
- Plan: `plan/PLAN.md` — one file, ordered by the pipeline: overview (§1), the shared layer the five stages stand on (§2), then one section per stage (§3–§7), extensions (§8) and wrap-up (§9). Each ParseBench gap is written out inside the stage it lands in, and each section ends with that stage's slice of the checklist. `plan/plan.html` is the illustrated version for the user.
- Running example in every spec doc: hospital ER wait times (3 hospitals × 4 departments × 3 severity levels, 900 rows).

## Pipeline

Five stages, one forward data flow. **The whole pipeline makes exactly two LLM calls**: 01 writes the data, 02 writes the words. Neither emits a data value, a key or a box. Everything else is program.

Each spec doc opens with a worked example and tags every step `[LLM]` or `[规则]`; keep that convention when editing them.

| Stage | Package | In → Out | LLM |
|---|---|---|---|
| 01 data | `s01_data` | domain pool → FactTable + TableSchema | yes, one call: writes the scenario prose, the generating script, and the intents already bound to columns. Parsing, enumeration, the coverage check, execution and the structural check are all program |
| 02 figure | `s02_figure` | table + schema → FigureSpec | yes, one call, after the figures are chosen: the title, subtitle and unit of each, plus a readable name for every column. Choosing, deriving, sampling and rejecting are all program |
| 03 render | `s03_render` | FigureSpec + StyleVector → image + L0/L1 | no |
| 04 record | `s04_record` | RenderOutput → Record (3 layers + `readable`) | no |
| 05 output | `s05_output` | Record → training target files | no |

Shared layer: `interfaces/` (six data interfaces), `registry/` (`charts.py` condition table, `conditions.py` predicate, `channels.py` readability), `common/` (seeds, geometry, pixel readback, cache), `report.py` (the readable view of an artifact: Mermaid diagrams and a terminal summary, written automatically beside every schema — a new stage adds a section here rather than a script under `tools/`).

`tools/build_report.py` turns one finished run into `plan/reports/report.html`: a single self-contained page, one section per stage, sixteen worked examples, every image embedded. Nothing on it is written by hand -- every number is read back off the artifacts the run left behind, and the reward check is re-run while the page is built. It takes its stylesheet out of `plan/plan.html` so the two cannot drift apart.

`tools/build_review.py` writes `review/`, whose `index.html` is the entrance to
everything generated: a page per stage, `gallery.html` with every figure the run drew,
a page per chart type, `diversity.html` (one figure redrawn under six style vectors,
where the recorded answers have to come back identical) and `checks.html` -- how the
code was verified rather than what it drew. The index counts the pictures on every
other page as it writes them, so it is built last. The chart-type
pages are drawn at build time from `tools/gallery.py`, which holds one binding per
declared type and calls no model, so `tests/unit/test_shapes.py` reads the same table
to check that no declared type is left undrawn. `tools/reportkit.py` holds what both
site builders share. `tools/mutation.py` injects one fault at a time into a throwaway
copy of the source and reports whether the tests catch it; a survivor is a test to
write, not a number to report.

`src/llmkit/` is a separate package that knows nothing about chartgen: model calls, JSON-mode with feedback retry, on-disk response cache, embedding dedup, concurrent batch. 01 uses it; so will any future multi-model evaluation. Adding a provider is one file.

## How the tricky parts work

- **The domain pool has two axes, not one.** `subject` is what the data is about; `register` is who published it and for whom. Asking only for subjects is what produced the pool this replaced: seventeen areas spanning aviation, banking, farming and sport, every one of them written as an operations dashboard — municipal transit and clinical trials included. A register decides the vocabulary a subject is written in: who the entities are, what one row is, how often it is published, and whether the numbers can go negative. Fourteen subjects × six registers give 46 declared cells, and the taxonomy is the stopping rule: a target count that stops early throws away topics already generated and leaves no trace in the file that it did.

- **The data call: one call, three outputs.** Scenario prose, the declaration script, and the intents — each intent carrying its target columns, aggregate, and view class — all come out of the same call. The script *is* the formalized scenario, so splitting this into two calls would insert a lossy JSON layer (hierarchy, orderedness, units and additivity are not explicit in prose) with no feedback path back upstream. Because the columns and the intents are written together, intent binding holds by construction rather than by inference.
- **Feasibility is decided at declaration time.** Structural and semantic conditions depend only on column declarations (`dim` value lists give cardinality; `time` start/end/freq give point counts; `additive` and `ordered` — `None` / `"ordinal"` / `"stage"` — are declared fields). 01 asks only whether each family is non-empty; it never expands the combinations. Only variance / distinctness / actual cell counts need real data.
- **The words call: one call per scenario, after the figures are chosen.** It judges no feasibility, picks no view, and produces no value, key or box; what comes out is the text that gets painted on the page. Every figure gets a title, not only the ones built from an intent: the intent split is about the **caption**, which is a training target and says what cannot be read off the image, while a title is drawn and every figure needs one. Filling three titles from intents and five from a template would put two audibly different registers in the corpus. It is checked for numbers, because a title painted on the image is read as truth there, and falls back to templates with no model reachable.
- **02 chooses nothing with a model, and there is no candidate list.** Three kinds of figure, three mechanisms, and only one needs a random number:
  - **意图图 / intent figure — constructed.** The binding fixes columns, aggregate and family; the condition table fixes the type; a deterministic order breaks ties. Its value is caption: only an intent figure's caption carries information not readable off the image.
  - **多面板图 / multi-panel — derived.** The anchor must be a figure already accepted standalone (so the shared view yields a free paired sample), and the partner panel is computed by the relationship rule.
  - **轮转图 / rotation — sampled with rejection.** Per family, draw (type, columns, aggregate), validate, project, admit or redraw, up to T tries.
  Never reintroduce enumeration here. Enumerating every legal view means hundreds to thousands of candidates, each needing a full projection pass, to ship about a dozen figures. The rotation prefers types the batch does not hold yet and narrows its draw by the declared semantic conditions **before** drawing, which is reading declarations rather than enumerating candidates.
- **Diversity is an admission test, not a count.** Reject a candidate when the batch already holds a figure with the **same key set and the same mark shape** — no threshold to tune. That pair is the right one because the output unit is `(key, value, box)`. `K_max` is only a render/storage budget; a count admits eight variations of `bar(hospital × …)`. Multi-panel figures are exempt: their value is the layout form, and repeated keys are what makes them a paired sample.
- **Row filters live only in `panel.py`.** They serve exactly one relationship (time comparison) and are sliced off the anchor on demand, never a sampling dimension of ViewSpec.
- **Projection is always one SELECT, in four shapes.** Grouped scalar (bar family, line, area, category line, pie, heatmap, table chart, waterfall, funnel), grouped five-number (box, range bar, error bar, windsock), binned count (histogram), and **per-row with no grouping** (scatter). Scatter needs deterministic down-sampling to the type's point cap, and its L2 degenerates: `rows` is 1 per mark, and histogram's `rows` equals its `count`. The aggregate set follows the shape — `FIVE_NUM`, `BIN_COUNT`, `NONE` are not SUM/AVG/COUNT. The four are a branch point because value dict size, applicable data filters and L2 usefulness all differ.
- **The names describe how a figure was chosen**, not its importance. Never reintroduce "main / supplementary" — that reading is what confuses readers.
- **Every segment of a key records where it was read from** (`registry.KeySource`, nine values). A key is an ordered tuple and its segments do not share a source: on a two-panel figure the hospital comes off the panel title while the department comes off an axis tick, and one source per figure answers neither question. It is a property of the figure, not of the style — the same numbers drawn as one panel move the hospital into the legend, and as a page of two figures into the headings. A colour group is a second name every mark already has (a site reports to one region); it is added to the key only when that mapping is a function, because otherwise it is another grouping and would change what a mark covers.
- **Density is a band, not a constant.** `charts.DENSITY_BANDS` widens the mark-count ceiling and states the fact-table rows each band needs; a type's own floor never moves and the sparsest band reproduces every declared bound exactly. A table that cannot meet the floor drops the band rather than relaxing the per-cell minimum.
- **The style vector is a declarative table** (`STYLE_DOMAINS`): every dimension states its domain, its default, the function that draws it, and whether it can change which values are readable. Two meta-tests read it — every declared value must have a drawing branch, and a dimension marked as not affecting readability must leave the recorded answers bit-identical.
- **Derived figures are composed by rule** in `s02_figure/panel.py`, and a relationship has three places to put its second view: the same plotting area, another plotting area on the same image, and another image on the same page (`PAGE_RELATIONS`). Six relationships put the second view in **another** plotting area — small multiples (one panel per value, the only one whose legend covers several panels), facet, drill-down, time comparison, dual metric, part-whole — and three put it in the **same** one: two measures, one measure over two slices, a value with the spread around it. One relationship, three places to put it: that is why a panel holding two views is a composition rule and not a row in the type table. Which relations may be split across a page is declared: the overlay relations may not, because two views in one plotting area say these numbers are read against each other and a page separates them, and small multiples may not, because one legend covering several panels is the only source of the legend-binding target. Whether a page's members need a segment naming them apart is decided by whether their keys collide, not by which relation made them. **Which relation a scenario starts the list at moves with its scenario id** — a budget shorter than the list otherwise never reaches the last entries, and the sixth panel relation was drawn zero times in ninety-six figures. The scenario id and not the seed, because only the rotation may move when the seed does. Two overlaid views must have different mark shapes, or their boxes coincide and nothing in the record can tell them apart. Whether the overlay needs a second value axis follows from the units, not from the layout: different units always, and the same unit twenty times apart as well, because the flattened series would fail the value self-check and take the figure with it. **A shared legend requires every panel to use the same series column** — a FigureSpec constraint the style vector cannot override.
- **A label written outside its mark takes the series colour when the plotting area holds two views**, and always gets a halo in the page background. One ink is enough while one view is drawn there. Two views put two sets of numbers between the same marks and leave a reader with position alone — and a printed value is matched exactly, so an unattributable label hands two marks one answer neither can be shown to carry. "Outside the mark" is not "over the background" either: on a band, an area or a dense scatter the position just past one mark is over another one.
- **A value label is kept only when it has clear space**: its box grown by two pixels must meet neither another label nor a tick label. A share of overlap cannot see the case it most needs to — two labels that butt against each other overlap by nothing and read as one string. A tick label counts because it is where a key is read from, so a number written across one costs a key as well as a value.
- **The category axis slants before it shrinks.** `label_rotation` is the floor a batch asks for; fitting raises it to 30° or 45° when the names do not fit side by side, and never to 90° — a name on its side is legible and reads poorly. What was actually drawn is `Axis.tick_rotation`, because the style states the request and the record has to state the result.
- **Record while drawing.** Every mark writes its box, key, and values at the moment it is drawn, using the plotting library's own coordinate transform. Never draw first and parse the image afterwards.
- **Freeze layout.** Image size, dpi, the edge budgets and the axes rectangle are fixed before anything is drawn. Frozen means "settled for this rendering", not "one set for every figure": image size, dpi and margins are each a style dimension, and re-rendering under another vector may give another plotting area because that pass records its own boxes. Auto-layout is the other thing — it moves the plot area afterwards and silently invalidates every recorded box.
- **The image is cut into blocks and the plotting area is what is left** (`s03_render/draw/layout.py`). Each block states which edge it wants and how thick it is, the blocks on an edge stack outward from the plotting area, and the four edges leave the plotting rectangle. The default placement reproduces the margins it replaced to the pixel. Two fixed strips of the top and bottom margin was the answer to a question real pages answer differently page to page — a legend runs down the right of one report and across the bottom of the next — so which edge a block takes is a style dimension (`legend_edge`), and moving one is a table edit. A block moved to a side brings its own thickness, because the left and right budgets are all gutter: a side legend is measured from its names, and a name is never cut to fit a block, because a legend is where a key is read from. What it fell back to is recorded — the style states the request, `Record.layout` states the result.
- **Readability is decided after rendering** from actual pixel geometry plus the encoding channel. Length and position are graded against what one pixel of their axis is worth; an angle is graded the same way against what its radius pins a share to (`3 * 2 / (2*pi*r)`); a colour scale is quantised and non-linear and is the one flat refusal. The rule is defined once, in `chart_types.md` §4. Unreadable marks drop out of value targets but stay in localization targets. A sector is asked about its `share`, not its value: the angle gives only the share, and a pie writes the total nowhere — which entry a target asks about is `Mark.value_key`, written beside `readable` because the two are one decision. A mark summarising a group holds five numbers and none of them is "the" value: it is asked about the far edge of the pair its box runs between (`q3` for a box, `max` for an error bar or a windsock), taken from the same table the readback measures against, so what is asked and what can be checked cannot drift apart. Asked about the median instead, the answer sits somewhere inside the box with nothing on the page fixing it — thirty-eight such marks went out as value targets the reward path could not check.
- **Three self-checks on the production path** (`s04_record/selfcheck.py`): is there anything inside the box, does the value read back from pixels match, does the answer stay the same under a different style. Failure discards the figure and logs the reason. The third one needs no extra render — it consumes the style-paired versions that are a product in their own right.
- **The first two self-checks are also the RL reward.** They need only the image and the claimed `(value, box)`, not ground truth. `common/readback.py` holds the one implementation; `s04_record/selfcheck.py` feeds it the renderer's record, `s05_output/verify.py` feeds it the model's output.
- **Visual variants live in the style vector, not the type table.** Two "types" whose four condition columns, mark shape and value dict are identical (solid pie vs. donut) occupy one row in `registry/charts.py`; the difference is a `StyleVector` field.
- **One coordinate convention**: pixels, origin top-left, `[x0, y0, x1, y1]`, image size recorded alongside.
- **Every block keeps its room whether or not it holds anything** — the text block, the legend block, the gutter on the right for a second value axis. `occupied` decides only what the fitting passes treat as a limit; it never changes a box. A block that shrank when it was empty would move the plotting area and invalidate every box already recorded against it.
- **A tick label is recorded with its own box**, category `axis_tick`. A mark already records that its key came off an axis tick; the box says which tick, which is the same claim about a key that `(value, box)` is about a value. It stays out of the page-element target, whose vocabulary is the benchmark's — there the whole chart is one `Picture`. Recording it caught two layout defects the same day: an axis title pulled up onto its own tick labels when the bottom margin ran out, and a slanted tick label on a grid reaching into the next row's panel-title strip. Both cost a key, and neither was visible before the boxes existed.
- **What the exporter hands over is a parameter, not the record's shape.** `key_scope` decides how much of a mark's address goes out (inside the plotting area, plus the panel it sits in, plus what only colour says), `granularity` decides one file per figure, per page or per batch, and `format` decides whether that file is the structured targets or a markdown document — granularity and format are separate questions, and neither implies the other. `output.preset` packages the four for one benchmark (`parsebench`: page, markdown, full scope, the grounded table); anything named explicitly beside it wins. All of it is written into the artifact: a key the model returns cannot land back on a mark if the scope it was asked under is unknown. In the markdown, each table is introduced by the figure number and title that were **drawn on the image** — `f08_v0` names a file and is on the page nowhere — and every key segment takes its own column.
- **Keys are ordered string tuples** — `("Mercy General", "Surgery")`. All three record layers join on `(figure_id, panel_id, key)`.

## Code Standards

- **Simple, short, clear** — the minimal implementation that solves the problem. No premature abstraction, no oversized files.
- **One file, one responsibility.** Anything used by two stages lives in `common/`, `registry/`, or `interfaces/`.
- **Extract a helper the second time a pattern repeats**, not the first, never the third.
- **Type hints everywhere**; avoid `Any`. `@dataclass` for every structured object, not loose dicts.
- **Stages talk only through `interfaces/`** — no stage imports another stage's internals.
- **Determinism**: `(input, seed) -> output` bit-for-bit. No global random state, no hidden mutation.
- **Split drawing code by mark shape, not by chart type** — 17 chart types, 6 mark shapes. The table is the product of a projection shape and a mark shape; every cell of `charts.GRID` either names the types in it or says why it is empty, so a missing kind of chart is found by reading a grid.
- **Atomic grain**: one fact-table row = one event. Aggregation happens only in the 02 projection, and three chart shapes there do not aggregate at all.

## Don'ts

- Don't name a chart type in either prompt — scenarios come from the domain, not from visualization templates, and the words call names what is drawn without choosing it. Intents stop at the view class.
- Don't aggregate at generation time.
- Don't let a model judge feasibility, pick a view, or write a value, a key or a box; don't add a third call; don't reintroduce enumeration into 02.
- Don't let a title state a finding. It is painted on the image and read as truth there, and the check that rejects numbers in one is not optional.
- Don't split the scenario back out into its own LLM call or its own stage interface.
- Don't re-render a figure to fix it. If a value can't be read off the image, drop it from the value targets. (Rendering the same FigureSpec under a *different* style vector is a product, not a retry.)
- Don't add a second plotting backend before the style ablation demands it.
- Don't add a chart type whose four conditions duplicate an existing row — make it a style dimension.
- Don't write ground truth that wasn't recorded during drawing.
- Don't change a data interface without also updating its sample in `tests/samples/` and its `schema_version`.
- Don't describe changes relative to an earlier version of the spec — the spec states only what is current.

## Scope note on other outputs

The recorded metadata (scenario, fact table, schema, FigureSpec, three record layers, style vector) supports more than the nine training targets: QA pairs, chart code, style-paired samples, layout-paired samples, multi-figure consistency sets. These are extra export functions over the same records, not extra pipeline runs. QA generation is deliberately out of the current line of work, but the record must keep everything it would need — `key`, aggregated values, row counts, dependency graph.
