# 03 · 动作空间设计

> **回答的三个问题：**
> 1. 现有 5 个 action（[storyline §4](../storyline/research_storyline_zh.html)）是否完整？哪些该加该删？
> 2. `request_view` 的输出形式应该是 SQL / NL / JSON？
> 3. 支持哪些图表类型？怎么从 request 转成实际图？

---

## TL;DR

1. **保留 4 个 action**：`request_view`, `commit_belief`, `answer`, `terminate`；**`point` 折叠进 `answer`** 的 bbox 引用。
2. **`request_view` 输出结构化 JSON ViewSpec**——既不是 SQL 也不是 NL。
3. **首发 8 种图**（bar / grouped_bar / line / area / pie / stacked_bar / scatter / heatmap），matplotlib 渲染 + 自定义 bbox collector 导出 element-level 坐标。

## 3.1 现有 action 的取舍

### 评价表

| Action | 现有定位 | 评价 | 建议 |
|---|---|---|---|
| `request_view` | 请求新图，−1 $B_v$ | **核心，保留** | 改输出形式（见 3.2） |
| `point` | 在已有图上局部检查，−1 $B_p$ | **模糊，建议折叠** | 与 `answer` 的 bbox 引用重复，没必要单设 |
| `commit_belief` | 更新假设状态，免费 | 保留，**但结构化** | 改成 schema 化输出 |
| `answer` | 提交答案，免费 | 保留 | 必须带 bbox refs |
| `terminate` | 关闭案例，免费 | 保留 | 加 early-termination reward |

### 3.1.a 为什么 `point` 应该折叠

直观比喻：现有 `point` action 像"我先指出这张图的左上角"，但 agent 答 `answer` 时**已经被强制要求引用 bbox**——这两个动作做的是同一件事。

| 当前 | 建议 |
|---|---|
| agent: `point(view=v1, region="periphery")` → 返回 zone label = "outer ring" → `answer("...")` | agent 直接 `answer("...", evidence=[(v1, element_id="outer_ring_cell")])` 一步到位 |

**收益：** action 空间从 5 减到 4，预算只剩一种（$B_v$），实验设计更简洁，reviewer 也不会问 "$B_p$ 设多大合理"。

**代价：** 失去了一个独立的"局部探索 vs 整图请求"的轴。如果你**真的**想在论文里做 $B_p$ 的 ablation，再保留。否则建议砍掉。

### 3.1.b `commit_belief` 必须结构化

现状只规定"用 bbox 证据更新案例理论"——但更新是自由文本就没法机评。

改成：

```json
{
  "hypothesis_id": "h_2",
  "action": "accept",
  "confidence": 0.85,
  "supporting_views": ["v_3"],
  "supporting_bbox": [{"view": "v_3", "element": "outer_ring"}],
  "note": "外环接单率 82% → 41%（自由文本，可选）"
}
```

### 3.1.c `terminate` 的 reward shaping

```
+ bonus if early-terminate ∧ answer correct
0      if fully-consumed terminate
- penalty if hallucinate on Schema-Unanswerable (即"应该 terminate 但没有")
```

这一条让"知道何时停止"成为可优化的目标，而不只是后置评分。

### 3.1.d 可选新增：`refine_view`

```python
refine_view(view_id, modification: ViewSpecDelta) -> PNG  # 成本 = 0.5 B_v
```

允许 agent 把已请求的图重新参数化（换 group_by、加 filter、改 aggregation）。

**何时加：** reviewer 必问"为什么不能编辑现有 view"。如果不加 `refine_view`，需要在 paper 里明确解释 refinement 已 fold 进 `request_view`。

**建议：** 第一版不加，预留接口。等收到 reviewer feedback 再说。

## 3.2 `request_view` 的输出形式：三选一

### 对比矩阵

| 形式 | Executability | 可解释性 | 对 VLM 友好度 | 在论文里的含义 |
|---|---|---|---|---|
| 原始 SQL | ★★★ | ★★ | ★ | "我们测的是 text-to-SQL 能力" — **偏题** |
| 自然语言 spec | ★ | ★★★ | ★★★ | "我们测的是 NL 理解" — **解析失败率不可控** |
| **结构化 JSON ViewSpec** | ★★★ | ★★★ | ★★ | **推荐** |

### 推荐方案：复用 Phase 3 的 ViewSpec

[phase_3.md §3.1.1](../data_generation/phase_3.md) 已经定义了 `ViewSpec`，直接复用：

```json
{
  "chart_type": "heatmap",
  "filter": "algorithm == 'new'",
  "group_by": ["zone", "time_window"],
  "agg": {"accept_rate": "AVG"},
  "select_columns": ["zone", "time_window", "accept_rate"]
}
```

### 为什么 JSON 胜出

1. **可执行性**：直接喂给 `extract_view(M, spec)`，零歧义。
2. **可评分**：可以自动判断 agent 请求的 view 是否在 `enumerate_views()` 的 feasible set 里——**非法 view 等价于浪费 $B_v$**，这是 active exploration quality 的强信号。
3. **可解释性**：每个字段都有清晰语义，agent 的"意图"是结构化的，可以做 view-selection trajectory 分析。
4. **避开 SQL 测试**：reviewer 不会说"你们其实测的是 text-to-SQL"。

### 对 VLM 友好度的补偿

担心闭源 VLM 不擅长结构化输出？三层兜底：

| 层 | 怎么做 |
|---|---|
| **Prompt 层** | system prompt 附 schema metadata + ViewSpec 字段表 + 3 个 one-shot 示例 |
| **解析层** | 自由文本 → ViewSpec **确定性 LLM 解析器**（温度 0，单独评估失败率，附录数字） |
| **重试层** | 解析失败时给 agent 看错误信息，允许一次"补救"重写，**不计 $B_v$** |

注意：解析层的失败率必须作为附录独立 metric 报出来（"GPT-4o ViewSpec 解析成功率 92%"），这样 reviewer 不会怀疑你的主要数字。

### SwiftEats 翻译

agent 在 B1 (READ) 步要请求"看 18 min 的时间窗口边界"：

```json
{
  "chart_type": "stacked_bar_chart",
  "filter": "algorithm == 'new'",
  "group_by": ["order_id"],
  "agg": {
    "click_to_assign": "AVG",
    "assign_to_pickup": "AVG",
    "pickup_to_dropoff": "AVG"
  },
  "select_columns": ["order_id", "click_to_assign", "assign_to_pickup", "pickup_to_dropoff"]
}
```

→ 渲染出 stacked bar 显示完整生命周期 → agent 看到 headline 只覆盖最后一段。

## 3.3 渲染管线 + bbox 导出

### 整体管线

```
agent: request_view(ViewSpec)
   │
   ▼
extract_view(M, ViewSpec)  ── deterministic SQL projection ──▶  DataFrame
   │
   ▼
render_chart(DataFrame, chart_type)
   │
   ├──▶ chart.png                          (给 agent 看)
   └──▶ chart_bbox.json                    (给评分器看)
              {
                "elements": [
                  {"id": "bar_xiehe",
                   "label": "Xiehe",
                   "bbox": [x1, y1, x2, y2],
                   "value": 6200},
                  ...
                ]
              }
```

> **关键设计：** agent 看到的是 PNG，**但评分器读 bbox JSON**——这是 channel 隔离的物理基础（见 [04 Exp A Channel Ablation](04_实验与baseline.md)）。

### bbox 怎么从 matplotlib 拿

```python
import matplotlib.pyplot as plt

def render_with_bbox(view_data, chart_type):
    fig, ax = plt.subplots()
    artists = render_dispatcher[chart_type](ax, view_data)
    fig.canvas.draw()

    bbox_layer = []
    for artist in artists:
        bbox = artist.get_window_extent(fig.canvas.get_renderer())
        bbox_layer.append({
            "id": artist.get_label() or f"{type(artist).__name__}_{id(artist)}",
            "label": artist.get_label(),
            "bbox": [bbox.x0, bbox.y0, bbox.x1, bbox.y1],
            "value": artist._chartagent_value  # 我们自定义的属性
        })

    fig.savefig("chart.png", dpi=120)
    with open("chart_bbox.json", "w") as f:
        json.dump({"elements": bbox_layer}, f)
```

每种 chart_type 的 `render_dispatcher` 都要把 numerical value 通过自定义 attribute 挂到 artist 上——这样 bbox 不只是几何坐标，还携带语义。

### 工程量

预估 1.5 人周：8 种图 × 每种 30 分钟到 1 小时写一个 `render_dispatcher` 入口 + 通用 bbox collector。

## 3.4 支持的图表类型

### 首发推荐：8 种

| 家族 | 图表 | 在 SwiftEats 案例里的作用 |
|---|---|---|
| Comparison | bar_chart | headline 31 vs 18 min 对比 |
| Comparison | grouped_bar_chart | 新 vs 旧 × 各阶段 |
| Trend | line_chart | 时间序列趋势 |
| Trend | area_chart | 堆叠成分变化 |
| Composition | pie_chart | 订单结果占比 |
| Composition | stacked_bar_chart | 订单生命周期 funnel-like view |
| Relationship | scatter_plot | 配送时间 vs 距离散点 |
| Relationship | heatmap | 区域 × 时段接单率 |

### 为什么不全 16 种

radar / treemap / violin 在真实分析师工作流的频度低，而且 **VLM 在这些 chart 上的表现差异更多来自训练分布，不是协议本身**——会污染 active exploration 的信号。

> 首发版本想要的是**"在标准分析图表上，active exploration 的优势能不能稳健地展现出来"**，而不是 "VLM 见过多少冷门图表"。

第二版可以补到全 16 种作为"chart coverage extension"。

### 数据 → 图的对应（已在 [phase_3.md §3.1](../data_generation/phase_3.md)）

ViewSpec 的 `column_binding` 决定了 chart 选择：

| Chart | 必须的列角色 |
|---|---|
| bar_chart | 1 categorical + 1 measure |
| grouped_bar_chart | 2 categorical + 1 measure |
| line_chart | 1 temporal + (1 series categorical) + 1 measure |
| area_chart | 1 temporal + 1 stack categorical + 1 measure |
| pie_chart | 1 categorical + 1 measure |
| stacked_bar_chart | 2 categorical + 1 measure |
| scatter_plot | 2 measure + (optional 1 categorical for color) |
| heatmap | 2 categorical (row × col) + 1 measure |

这表本来就是 Phase 3 enumerate_views 的逻辑，直接复用。

## 3.5 章节小结

| 子主题 | 一句话 | 必做 |

| Action 取舍 | 4 个 action（`point` 折叠）+ 结构化 commit_belief + early-term reward | 改 action 接口 |
