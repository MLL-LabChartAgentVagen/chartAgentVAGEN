# 01 · 数据与问题构建

> **回答的三个问题：**
> 1. Agent 起步时应该看到什么？（$D_0$ 的设计）
> 2. 问题的难度怎么分级？
> 3. 要不要设计"答不出来的题"和"骗人的题"？

---

## TL;DR

1. **$D_0$ 必须是实验变量**，分 Floor / Realistic / Adversarial 三档跑。
2. **难度用 $k^*$**（理论最小所需视图数）替代 Phase 3 现有的 `#ops`。
3. **必须**强制混入 ≥ 25% 的"带毒题"——这是 LDW 区别于所有 chart QA benchmark 的唯一题型。

---

## 1.1 $D_0$（初始仪表板）的设计

### 问题

[research_storyline_zh.html §3.1](../storyline/research_storyline_zh.html) 规定 $D_0$ = "2–4 张不完整的图表线索"——但**这 2–4 张是怎么选出来的？**

这看起来是个细节，其实是个**最大的隐藏自由度**：如果 $D_0$ 随机选，agent 表现的提升可能只是因为 $D_0$ 选得太差，**任何方法都能赢**。

### 直观比喻

把 $D_0$ 想成"案件现场照片"：
- 如果给侦探的照片是**正中目标的特写**——任何业余者也能破案
- 如果给的是**对面墙的随机一角**——专业侦探也无能为力
- 真正能测出侦探水平的，是**模糊但可推断**的照片

所以 $D_0$ 必须三档都做。

### 实施方案

| 档位 | 怎么构造 $D_0$ | 主要测试的能力 | 在论文里的作用 |
|---|---|---|---|
| **Floor**（信息饥饿） | **不给任何图**，只给 schema + scenario_title + 问题集 + 假设集 | 纯探索策略（看 agent 能否盲选关键视图） | 上限信号 |
| **Realistic**（默认） | 从 Phase 3 enumerate 出的合法视图中**随机抽 3 张** | 综合 | 主表数字 |
| **Adversarial**（含毒） | **强制**含 1 张由 dashboard illusion injector 构造的误导性 headline 图 | Debunk 能力 | 主推 figure（对应 SwiftEats Figure 1） |

### SwiftEats 翻译

| 档位 | 看到的 $D_0$ |
|---|---|
| Floor | 只有"SwiftEats 周一发布新 AI 调度算法，记者要核实 18 分钟是真的吗"这段文字 |
| Realistic | 随机 3 张图：[配送时长 line chart] + [订单量 bar chart] + [按订单类型的 pie chart] |
| Adversarial | **必含**那张红绿对比的 31→18 min headline 图 + 另 2 张随机视图 |

### 关键的 fairness 校验

Adversarial 档的 $D_0$ 必须自动满足：
- **$\text{answer-from-}D_0\text{-alone}$ 是错的**（且与 ground truth 可证伪冲突）
- 这一条写进 [phase 3 QA 生成器](../data_generation/phase_3.md) 的 acceptance criterion，自动检验

伪代码：
```python
def is_valid_adversarial_D0(D0_views, true_answer, schema):
    naive_answer = answer_from_views_alone(D0_views)  # 跑一个 closed-form 推理
    return contradicts(naive_answer, true_answer)
```

### 不这样做的代价

reviewer 会问：
- "你们的 $D_0$ 都是随机的，所以 agent 的主动请求只是在补足平庸 baseline。试一下当 $D_0$ 已经是最优 4 视图时，agent 还能否提升？"
- "为什么 active exploration 的优势不会被 '$D_0$ 选成对答案最有用的 3 张' 的随机性掩盖？"
- "你们测的到底是模型的探索策略，还是 $D_0$ 设计者的恶意？"

→ 三档全做 + 公开构造规则 = 三个问题一次性堵死。

## 1.2 难度分级：用 $k^*$ 替代 `#ops`

### 问题

[phase_3.md §3.5](../data_generation/phase_3.md) 用 **#ops** 度量难度——这适合"给定视图后的算子链长度"，但**对 LDW 是错位的**。

一个 1-op 问题（"哪个城区接单率最低？"）如果 $D_0$ 里没 zone heatmap：**任何**算子都解不出。这时真正的困难不是算子，是**搞到正确视图**。

### 新的难度度量：$k^*$

$k^*$ = "对这个问题，理论上最少需要请求多少张新视图"。

| $k^*$ | 难度档 | 例子 |
|---|---|---|
| 0–1 | Easy | $D_0$ 已含答案 / 请求 1 张就能答 |
| 2 | Medium | 需要 2 张相关视图协调 |
| 3 | Hard | 需要 3 张：通常 Reveal + Reconcile 都要 |
| 4+ | Very Hard | 跨 4 个能力的完整调查（如 SwiftEats 4-beat） |

### 怎么自动算 $k^*$

确定性算法，放进 Phase 3 的 QA 标注阶段：

```python
def compute_k_star(question, ground_truth_answer, schema, D0):
    # 1. 反向搜索能闭合答案路径的最小视图集
    required_views = backward_search(ground_truth_answer, schema)
    # 2. 减掉 D0 里已有的
    missing = required_views - set(D0.views)
    return len(missing)
```

实现上：在 [phase 3 operator algebra](../data_generation/phase_3.md) 里，每个 question 已经是一条 typed pipeline，可以反向跟踪每个 operator 用到的列，再映射回需要的视图。

### 两轴交叉的完整分级

| | $k^* = 0\text{–}1$ | $k^* = 2$ | $k^* = 3$ | $k^* \geq 4$ |
|---|---|---|---|---|
| **#ops 1–2** | Easy | Medium | Hard | Very Hard |
| **#ops 3–4** | Medium | Medium-Hard | Hard | Very Hard |
| **#ops 5+** | Hard | Hard | Very Hard | Very Hard |

最终 difficulty label = max(`#ops` 档, $k^*$ 档)。

### SwiftEats 翻译

| 题目 | $k^*$ | #ops | 难度 |
|---|---|---|---|
| "headline 的时间窗口是 t₀→t₃ 还是 t₂→t₃？" | 1 | 1 | Easy |
| "新算法下，外环区域的接单率变化多少？" | 2 | 3 | Medium |
| "'送得更快 ∧ 体验更差'同时为真，找到协调结构" | 3 | 4 | Hard |
| "全口径修正后，headline 是否还成立？" | 4 | 5 | Very Hard |

### 不这样做的代价

- "你们说 LDW 测的是探索策略，但难度还是按答完之后的算子数算的——agent 真实困难是'从 $D_0$ 到能算的状态'之间的 gap，你们没量化。"
- "如果 $B_v$ 够大，所有问题都退化为 `#ops` 难度——你们整套协议其实没有难度梯度。"

## 1.3 带毒题：必须的 25%

这是**整个 LDW 唯一无法被 ChartMuseum / InterChart / ChartM3 比较**的题型。也是 [00 核心命门](00_核心命门.md) 那条 hallucination claim 的物理对应。

### 三类带毒题

| 类型 | 怎么构造 | 正确行为 |
|---|---|---|
| **A. Schema-Unanswerable** | 问的列**不在隐藏 $M$ 里**（例：用户性别） | agent 应 `commit_belief("insufficient")` 然后 `terminate` |
| **B. Budget-Unanswerable** | 问题的 $k^* > B_v$ | agent 应在用尽预算前停止 + 给 partial answer + 标 uncertainty |
| **C. $D_0$-Sufficient Trap** | $D_0$ 内已含正确答案，但 $D_0$ 呈现的是**对立结论**（dashboard illusion） | agent 应**至少请求 1 张视图**做交叉验证；纯靠 $D_0$ 答出（即使答对）按低分计 |

### SwiftEats 翻译

| 类型 | 示例 |
|---|---|
| A | "新算法把骑手的工时变化了多少？" — 隐藏 $M$ 里**没有 driver_hours 列**，这题无解 |
| B | "在 4 个区域 × 12 个月 × 3 个时段下的接单率分布？" — $k^* = 6$ 但 $B_v = 4$ |
| C | $D_0$ 只放那张 31→18 min headline 柱状图（裸数值），问 "新算法是不是真的提速了？" — 直接答 "yes" 即使表面答对，但因为没做任何交叉验证，按 trap-fail 计 |

### 实施

在 Phase 3 QA 生成器里强制配额：

```python
QUESTION_QUOTA = {
    "normal":              0.75,  # 标准多步推理题
    "schema_unanswerable": 0.10,
    "budget_unanswerable": 0.10,
    "D0_sufficient_trap":  0.05,
}
```

### 怎么打分

带毒题不能用普通 accuracy，要用专门指标：

| 题型 | 评分逻辑 |
|---|---|
| Schema-Unanswerable | `commit_belief("insufficient")` 计满分；自信答非"insufficient"且 wrong 计 0 + 进 **hallucination rate** 计数器 |
| Budget-Unanswerable | partial answer + uncertainty mark = 满分；坚持给完整答案 = 部分扣分 |
| $D_0$-Sufficient Trap | 必须有 ≥ 1 次 request_view 才能拿满分；纯 $D_0$ 答即使对也只能拿 50% |

详见 [04 §metrics](04_实验与baseline.md)。

### 不这样做的代价

- "你们的 4 能力（Read/Reveal/Reconcile/Debunk）只是标签，模型只要 always-request-max-budget 就能通关，根本不需要'知道何时停止'。"
- "VLM 永远会自信作答的问题不在你们的 benchmark 里——这恰恰是真实场景里最危险的部分。"
- "你们的 storyline 一直在讲 dashboard illusion，但题库里没有一道能直接命中这个 illusion 的题。"

## 1.4 章节小结

| 子主题 | 一句话 | 必做改动 |
|---|---|---|
| $D_0$ 设计 | 三档：Floor / Realistic / Adversarial | 加 `DashboardIllusionInjector`（[02 §2.2](02_pipeline改进.md)） |
