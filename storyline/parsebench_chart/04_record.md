# 04 · 标注记录

把渲染时记下的东西拼成一份完整记录，判断每个值能不能从图上量出来，并做三项自检。

**这一阶段全部由程序执行，不调用 LLM。**

**子阶段**

| # | 子阶段 | 谁做 | 产出 |
|---|---|---|---|
| [2](#2-谁产出哪一层) | 拼接 L0 / L1 / L2 | 规则 | 一份完整记录 |
| [5](#5-值能不能读出) | 逐图元判定值能否读出 | 规则 | 每个图元的 `readable` |
| [6](#6-三项自检) | 三项自检 | 规则 | 通过则写盘，否则丢图并记原因 |

参考：[1 三层](#1-三层) · [3 记录字段](#3-记录字段) · [4 图元形状](#4-图元形状)

先看 [§0 示例](#0-示例)，只看那一节就能明白这个阶段在干什么。

## 0. 示例

输入是 [03](03_render.md#0-示例) 渲染出的条形图与它的几何。

### 第一步 · 拼接三层

三份记录各由知道它的组件写出，按 `(figure_id, panel_id, key)` 对齐拼起来：

```
L0  来自页面合成器   图表是一个 Picture，上方正文与下方图注是 Text
L1  来自渲染器       三个条的框、键、值；绘图区与 y 轴的值域像素域
L2  来自 02 的投影   Mercy General 372 行 · St. Luke's 315 行 · Riverside 213 行
```

拼完的Mercy General那个条：

```json
{"mark_id": "m0", "panel_id": "p0",
 "key": ["Mercy General"], "values": {"value": 42.3},
 "box": [168, 196, 278, 520],
 "channel": "length", "labeled": false,
 "rows": 372}
```

```json
{"panel_id": "p0", "box": [96, 60, 860, 520],
 "axes": [{"role": "y", "value_range": [0, 60], "pixel_range": [520, 60], "scale": "linear"}]}
```

### 第二步 · 判断值能不能量出来

这张图没写数值标注，条形的画法是长度，所以要算精度够不够：

```
每像素代表    60 分钟 / 460 像素 = 0.13 分钟
42.3 的 1%    0.42 分钟  =  0.42 / 0.13 ≈ 3.2 像素
3.2 ≥ 2       →  readable = true
```

三个条都通过，各自加上 `"readable": true`。

两个读不出的对照：

- 若风格采样让这张图与另一个面板共享 y 轴、值域变成 `[0, 6000]`，每像素代表 13 分钟，42.3 的 1% 只有 0.03 像素 → `readable = false`。图仍然产出三个条的位置，只是不产出它们的值。
- 同一批里的 `pie(department × SUM(wait_minutes))`，画法是角度。没写百分比标注时四个扇区全部 `readable = false`；写了标注则全部为 true 且容差为 0。

### 第三步 · 三项自检

```
框里有没有东西   取 [168,196,278,520] 内的像素，蓝色占比 96%     通过
量出来的值对不对  (520 − 196) × 0.13 = 42.1，与记录的 42.3 差 1.4 像素以内   通过
换风格答案变不变  另一份风格向量渲出的记录里，三个键对应的值仍是 42.3 / 35.8 / 28.1   通过
```

任何一项不过就丢掉这张图并记原因。

### 多面板图的差别

[02](02_figure.md#0-示例) 的图④是两个面板共享 y 轴与图例。记录里多出来的是：

```json
{"legend": [{"box": [820, 120, 890, 138], "maps_to_category": "Mercy General",
             "applies_to_panels": ["p0", "p1"]}]}
```

单面板图上 `applies_to_panels` 恒为一个元素，是平凡的；两个面板共用一个图例项时它才有信息量，这是`图例绑定`训练目标的全部来源。两个面板各自记一份 `panels[]`，图元用 `panel_id` 指向自己所在的面板。

### 输出

一份完整记录：三层数据 + 每个图元的 `readable`。[05](05_output.md) 只读这份记录，不需要知道事实表和渲染器。

## 1. 三层

```
L0  几何    页面上有哪些框、框是什么类别        纯像素事实，无数据语义
      ▲
L1  编码    框对应哪个键、哪个值，图例怎么映射   图 → 数据
      ▲
L2  来源    这个值由多少行原始记录聚合而来       数据 → 来源
```

| | 给谁用 | 前提 |
|---|---|---|
| **L0** | 页面级定位 | 任何渲染器 |
| **L1** | 带位置的转录、图例绑定 | 边画边记的渲染器 |
| **L2** | 下钻 | 一行一件事的事实表 |

三层各自可以单独关掉。L2 关掉重训是 [05](05_output.md#7-消融) 的关键消融。

---

## 2. 谁产出哪一层

每层由知道该信息的那个组件直接写出，没有哪个组件需要反推另一个组件的内部状态。

| 层 | 谁产出 | 什么时候 |
|---|---|---|
| L2 | [02](02_figure.md) 的投影器 | 聚合时顺带返回每组的 `COUNT(*)` |
| L1 | [03](03_render.md) 的渲染器 | 画每个图元时记下框、键、值 |
| L0 | [03](03_render.md) 的页面合成器 | 排页面元素时记下框与类别 |

拼接是查表连接，不做任何推断。

---

## 3. 记录字段

一条记录对应一张图像。

```
figure_id, image_path, image_size, style_vector, degradation

L0  elements[]     box, category ∈ {Text, Table, Picture, Page-Header, Page-Footer}

L1  panels[]       panel_id, box,
                   axes[]  → role ∈ {x, y, y_right}, value_range, pixel_range, scale
    marks[]        mark_id, panel_id, key, values{}, box,
                   channel, labeled, label_box, readable
    legend[]       box, maps_to_category, applies_to_panels[]

L2  marks[].rows   该图元背后的原始行数
```

- **`key` 是有序字符串元组**，例如 `("Mercy General",)`、`("Mercy General", "Surgery")`、`("2024-03", "Mercy General")`。它唯一确定这个图元对应表里的哪一组，也是 [05](05_output.md) 输出格式里的"键"。
- **`axes` 的 `value_range` 与 `pixel_range`** 是 [§5](#5-值能不能读出) 的全部输入。compound 图有 `y` 与 `y_right` 两条，各绑一个测度。
- **`legend[].applies_to_panels`**：共享图例下"这个图例项管哪几个面板"是模型的已知失败模式，这里零成本产出它的答案。
- **L2 存行数不存行**：需要真实的行时用 `key` 回去过滤事实表即可确定性还原，记录体积小一个量级。

---

## 4. 图元形状

不同图表类型的图元形状不同：条形是矩形带一个值，箱线是矩形带五个值，折线是点，散点是点带两个值。

**用组合表达，不用继承**：图元带一个值字典而不是一个标量。条形填一个键，箱线图填五个。下游对图元做的事完全一样——取框、取值——所以不存在需要多态的行为。

各类型的值字典键见 [chart_types.md §3](chart_types.md)。

---

## 5. 值能不能读出

逐图元判定，输入只有 L1 里的实际几何与该图元的画法。判据在 [chart_types.md §4](chart_types.md) 定义，本阶段只是执行它，结果写成 `readable` 字段。

读不出的图元从 [05](05_output.md) 的值目标里去掉，仍保留在定位目标里。饼图、热力图、树图整张图的值目标可能全空，这是判据的预期结果，不是缺陷——这些图仍然贡献定位目标。

---

## 6. 三项自检

记录写盘前必须通过，任何一项失败就丢掉这张图并记下原因。这三项是整个流水线的正确性底线——边画边记依赖绘图库内部的坐标变换，错了不会抛异常，只会安静地产出偏移的框。

| 检查 | 怎么做 | 挡住什么 |
|---|---|---|
| **框里有没有东西** | 回读渲染出的 PNG，取框内像素，检查该图元声称的颜色占比是否过低 | 框整体偏移、自动布局挪动了绘图区、dpi 换算错 |
| **量出来的值对不对** | 用框的像素位置与该面板的值域、像素域反算出值，与记录的值比对 | 轴映射错误、对数轴处理错误、负值与堆叠基线错误 |
| **换风格答案变不变** | 同一 FigureSpec 的两份风格版本，记录里的「键 → 值」集合必须完全相同 | 某个风格参数意外改了数据 |

前两项逐图元跑，第三项按图抽样跑。三项都在生产路径上，不是测试——边画边记的错误只会在真实数据上暴露，测试里的固定样例覆盖不到。

第三项不需要额外渲染。风格配对样本本来就要对同一份 FigureSpec 渲两份，这两份记录既是[消融与配对数据](05_output.md#4-同一份记录还能派生什么)，也是这项自检的输入——渲一次，两处用。

**前两项只用图像与模型自己的输出，不用 ground truth，因此同一段代码可以直接当作可验证奖励用在训练上。** 见 [05 §3](05_output.md#3-输出能自己验自己)。
