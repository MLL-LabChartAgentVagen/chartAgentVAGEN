# 05 · 标注记录

流水线在输出图像的同时，输出一份"画了什么"的结构化记录。三层，逐层信息严格增加，各自可以单独关掉。

**本文**
1. [三层](#1-三层) → 2. [谁产出哪一层](#2-谁产出哪一层) → 3. [记录字段](#3-记录字段) → 4. [图元形状](#4-图元形状) → 5. [值能不能读出](#5-值能不能读出) → 6. [三项自检](#6-三项自检) → 7. [示例](#7-示例)

---

## 1. 三层

```
L0  几何    页面上有哪些框、框是什么类别        纯像素事实，无数据语义
      ▲
L1  编码    框对应哪个键、哪个值，图例怎么映射   图 → 数据
      ▲
L2  来源    这个值由多少行原始记录聚合而来       数据 → 来源
```

| | 给谁用 | 前提 |
|---|---|---|
| **L0** | 页面级定位 | 任何渲染器 |
| **L1** | 带位置的转录、图例绑定 | 边画边记的渲染器 |
| **L2** | 下钻 | 一行一件事的事实表 |

分层同时对应不同的消费者、不同的渲染器能力要求、以及不同的可证伪性——L2 可以单独关掉重训，这是 [06](06_output.md) 的关键消融。

---

## 2. 谁产出哪一层

每层由知道该信息的那个组件直接写出，没有哪个组件需要去反推另一个组件的内部状态。

| 层 | 谁产出 | 什么时候 |
|---|---|---|
| L2 | [03](03_figure.md) 的投影器 | 聚合时顺带返回每组的 `COUNT(*)` |
| L1 | [04](04_render.md) 的渲染器 | 画每个图元时记下框、键、值 |
| L0 | [04](04_render.md) 的页面合成器 | 排页面元素时记下框与类别 |

三份记录按 `(figure_id, panel_id, key)` 拼成一条完整记录。拼接是纯查表连接，不做任何推断。

---

## 3. 记录字段

一条记录对应一张图像。

```
figure_id, image_path, image_size, style_vector, degradation

L0  elements[]     box, category ∈ {Text, Table, Picture, Page-Header, Page-Footer}

L1  panels[]       panel_id, box,
                   axes[]  → role ∈ {x, y, y_right}, value_range, pixel_range, scale
    marks[]        mark_id, panel_id, key, values{}, box,
                   channel, labeled, label_box, readable
    legend[]       box, maps_to_category, applies_to_panels[]

L2  marks[].rows   该图元背后的原始行数
```

几点说明：

- **`key` 是一个有序的字符串元组**，例如 `("协和",)`、`("协和", "外科")`、`("2024-03", "协和")`。它唯一确定这个图元对应表里的哪一组，也是 [06](06_output.md) 输出格式里的"键"。
- **`axes` 里的 `value_range` 与 `pixel_range`** 是 [§5](#5-值能不能读出) 的全部输入。compound 图有 `y` 与 `y_right` 两条，各自绑定一个测度。
- **`legend[].applies_to_panels`**：共享图例下"这个图例项管哪几个面板"是模型的已知失败模式，这里零成本产出它的答案。
- **L2 存行数不存行**：只记数量；需要真实的行时，用图元的 `key` 回去过滤事实表即可确定性还原。记录体积小一个量级，信息不丢。

---

## 4. 图元形状

不同图表类型的图元形状不同：条形是矩形带一个值，箱线是矩形带五个值，折线是点，散点是点带两个值。

**用组合表达，不用继承**：图元带一个值字典而不是一个标量。条形往字典里填一个键，箱线图填五个。下游对图元做的事完全一样——取框、取值——所以不存在需要多态的行为。

各类型的值字典键见 [registry.md §4](registry.md)。

## 5. 值能不能读出

**图上标的那个数，能不能从图上量出来。** 渲染完成后逐图元判定，输入只有 L1 里的实际几何与 [registry.md §5](registry.md) 的画法。结果写成 `readable` 字段。

```
写出了数值            → 能，容差 0
没写，画法是角度/面积/颜色  → 不能
没写，画法是长度/位置       → 1% 的值折算成像素 ≥ 2 时能，否则不能
```

第三条的算式：`每像素代表的值 = 值域跨度 / 像素域跨度`，`该值的 1% / 每像素代表的值 ≥ 2`。

读不出的图元从 [06](06_output.md) 的值目标里去掉，仍保留在定位目标里。判定结果是记录里的一个布尔字段，因此 06 导出目标时只需要读记录，不需要知道渲染器和事实表。

## 6. 三项自检

记录写盘前必须通过三项检查，任何一项失败就丢掉这张图并记下原因。这三项是整个流水线的正确性底线——边画边记依赖绘图库内部的坐标变换，错了不会抛异常，只会安静地产出偏移的框。

| 检查 | 怎么做 | 挡住什么 |
|---|---|---|
| **框里有没有东西** | 回读渲染出的 PNG，取框内像素，检查该图元声称的颜色占比是否过低 | 框整体偏移、自动布局挪动了绘图区、dpi 换算错 |
| **量出来的值对不对** | 用框的像素位置与该面板的值域、像素域反算出值，与记录的值比对 | 轴映射错误、对数轴处理错误、负值与堆叠基线错误 |
| **换风格答案变不变** | 同一 FigureSpec 用两个不同风格各渲一次，两份记录的「键 → 值」集合必须完全相同 | 某个风格参数意外改了数据 |

前两项逐图元跑，第三项按图抽样跑。三项都在生产路径上，不是测试——边画边记的错误只会在真实数据上暴露，测试里的固定样例覆盖不到。

## 7. 示例

接[渲染出的条形图](04_render.md#7-示例)。

协和那个条的 L1 记录：

```json
{"mark_id": "m0", "panel_id": "p0",
 "key": ["协和"], "values": {"value": 42.3},
 "box": [168, 196, 278, 520],
 "channel": "length", "labeled": false, "label_box": null,
 "readable": true, "rows": 372}
```

面板记录：

```json
{"panel_id": "p0", "box": [96, 60, 860, 520],
 "axes": [{"role": "y", "value_range": [0, 60], "pixel_range": [520, 60], "scale": "linear"}]}
```

**判定过程**：每像素代表 `60 / 460 = 0.13` 分钟；42.3 的 1% 是 `0.42` 分钟，折合 `0.42 / 0.13 ≈ 3.2` 像素，≥ 2，所以 `readable = true`。

**两个读不出的对照**：

- 同一张图，若风格采样让它与另一个面板共享 y 轴、值域变成 `[0, 6000]`，则每像素代表 13 分钟，42.3 的 1% 只有 0.03 像素 → `readable = false`。这张图仍然产出三个条的位置，只是不产出它们的值。
- 意图外的 `pie(department × SUM(cost))`，画法是角度。没写百分比标注时四个扇区全部 `readable = false`；写了标注则四个全部 `readable = true` 且容差为 0。

**自检**：取 `[168, 196, 278, 520]` 内的像素，蓝色占比 96%，通过；用 `(520 − 196) × 0.13 = 42.1` 反算，与 42.3 差 0.2 分钟、合 1.5 像素以内，通过；换一个风格重渲，三个键对应的值仍是 42.3 / 35.8 / 28.1，通过。
