# 01 · 场景

把一个抽象的领域变成一个具体、真实、能写出数据的业务场景。本阶段不生成任何数据。

**这一阶段** — **[LLM ×1]** 由子领域写出场景描述与分析意图；**[规则]** 领域池的采样与去重。

## 0. 示例

**输入** — **[规则]** 从 200+ 条的领域池里按复杂度分档抽一条：

```json
{"name": "急诊科运营分析", "topic": "Healthcare", "complexity_tier": "medium",
 "typical_entities_hint": ["医院", "科室", "分诊等级"],
 "typical_metrics_hint": [{"name": "wait_time", "unit": "分钟"}],
 "temporal_granularity_hint": "daily"}
```

**处理** — **[LLM ×1]** 把上面这条提示展开成一个具体场景：真实的机构名、带单位与合理范围的指标、明确的时间窗、以及这份数据被收集来回答什么问题。

**输出**：

```json
{"scenario_title": "2024 上半年 A 市三家三甲医院急诊科就诊与等待时间记录",
 "data_context": "A 市卫健委为评估急诊分流政策的效果，汇总了三家三甲医院 2024 年 1 至 6 月的逐次就诊记录。",
 "key_entities": ["协和", "华山", "瑞金", "内科", "外科", "儿科", "创伤", "轻", "中", "重"],
 "key_metrics": [{"name": "wait_minutes", "unit": "分钟", "range": [5, 120]},
                 {"name": "cost",         "unit": "元",   "range": [80, 3000]},
                 {"name": "satisfaction", "unit": "分",   "range": [1, 5]}],
 "temporal_granularity": "daily",
 "target_rows": 900,
 "analytical_intent": ["哪家医院、哪个科室的等待时间最长",
                       "等待时间在半年内怎么变化",
                       "等待越久是不是满意度越低"]}
```

**去重** — **[规则]** 对 `data_context` 做 embedding 检查，与已有场景余弦 ≥ 0.85 就丢弃重来。

到此为止一个数字都还没生成。`key_metrics` 里的 range 只是给 [02](02_fact_table.md) 的取值范围提示，不是数据。三条意图也还只是自然语言——此刻列还不存在。

## 1. 领域池

一次性构建、之后反复复用的 200+ 细粒度子领域池。两级：Topic → Sub-topic。

**怎么建**

```
1  [LLM]  生成 topic          一次产出 N 个互不重叠的行业级大类，把已有的 topic 传入避免重复
2  [LLM]  逐 topic 生成 sub-topic  每个 topic 下产出若干具体分析情境，附实体 / 指标 / 时间粒度提示
3  [规则] 去重                对名称做 embedding 检查，余弦 ≥ 0.80 的成对标出，删掉或重生成
4  [规则] 补齐                统计复杂度三档与 topic 覆盖，缺哪档补哪档，直到 200+ 且三档均衡
```

这四步只跑一次，产物是一个缓存文件。第 3 步的检查器只有一个实现，topic、sub-topic、场景三处共用。

**怎么采** — **[规则]**：按复杂度分档，档内无放回随机抽。某档抽掉 80% 后重置。抽样由随机种子决定，同一个种子给出同一串子领域。

## 2. 场景实例化

**[LLM ×1]**。输入是子领域的全部字段，提示词里带一个完整的输入-输出样例来固定格式。

| 字段 | 内容 |
|---|---|
| `scenario_title` | 含时间段、机构、分析焦点的具体标题 |
| `data_context` | 谁收集、为何收集、何时收集 |
| `key_entities` | 3–8 个具名实体，用真实世界的名字，不用「实体 A」 |
| `key_metrics` | 2–5 个可量化指标，每个带正确单位与合理取值范围 |
| `temporal_granularity` | hourly / daily / weekly / monthly / quarterly / yearly |
| `target_rows` | simple 200–500 · medium 500–1000 · complex 1000–3000 |
| `analytical_intent` | 2–4 条，见下节 |

子领域给的提示是软约束：具体场景需要时可以改写或替换，但不能越出该子领域的范围与复杂度档位。

## 3. 分析意图有什么用

一条分析意图就是一句话：**这份数据被收集来回答什么问题**。它在后面有两个具体用途。

### 用途一：从几百个候选里挑出该画的那几张

[03](03_figure.md) 会从这张表枚举出两百多个合法视图，光 `bar` 就有 30 个（5 个类别列 × 6 种聚合）。要画哪几张？

意图给出答案。意图① 在 [02](02_fact_table.md#42-意图绑定) 被绑成「目标列 `hospital × wait_minutes`，视图类 比较」，03 按这两项一匹配，30 个 bar 候选里只剩一个 `bar(hospital × AVG(wait_minutes))`。

真实报表里的图是为了回答问题才画的，不是为了覆盖图表类型才画的。意图把这件事带进了生成流程。

### 用途二：caption 的内容来源

caption 是[八类训练目标](06_output.md#2-训练目标)之一，而 caption 必须和图对得上。

```
有意图   "本图比较三家三甲医院急诊科的平均等待时间，用于评估 2024 上半年分流政策的效果"
没意图   "各医院平均等待时间"      —— 只能复述坐标轴名
```

### 它管的范围

意图只管**主图**。[03 §5](03_figure.md#4-挑图) 还会按图表族轮转补几张图，用来撑住类型覆盖面；那些图没有对应意图，caption 由视图本身的描述生成。一个场景 8 张图里，通常 3 张有意图、5 张是补充。

### 视图类的六个取值

与 [chart_types.md](chart_types.md) 的族一一对应。**本阶段只写自然语言，不写视图类**——此刻列还没定义，硬指定容易和后面的 schema 对不上，绑定在 [02](02_fact_table.md#42-意图绑定) 做。

| 视图类 | 什么样的问题 |
|---|---|
| 比较 | 谁最高、谁最低、排序 |
| 趋势 | 随时间怎么变、什么时候拐弯 |
| 构成 | 谁占多大比例、构成怎么变 |
| 关系 | 两个指标是不是一起动 |
| 分布 | 散得开不开、有没有离群 |
| 流程 | 一步步流转下来在哪一步掉得最多 |

## 4. 约束

- 本阶段不出现任何图表类型词汇。数据源于业务需求，图表是数据的投影，选择权在下游。
- 所有数字、实体、时间窗口须落在合理的真实世界范围内。
- 严格 JSON 输出，无附加说明。

## 附录：领域条目

```json
{
  "id": "dom_001",
  "name": "ICU 床位周转分析",
  "topic": "Healthcare",
  "complexity_tier": "complex",
  "typical_entities_hint": ["医院", "ICU 病区", "患者类别"],
  "typical_metrics_hint": [{"name": "occupancy_rate", "unit": "%"},
                           {"name": "length_of_stay", "unit": "天"}],
  "temporal_granularity_hint": "daily"
}
```

池文件另存版本号、生成时间、复杂度分布与 topic 覆盖统计。

| 复杂度 | 含义 |
|---|---|
| simple | 单一实体类型，1–2 个指标，直接的时间序列 |
| medium | 多个相关指标，2 个以上实体类型 |
| complex | 嵌套层级，3 个以上相互依赖的指标 |
