## 2. Phase 1 的唯一改动：分析意图

现有 scenario 输出已包含 `scenario_title`、`data_context`、`key_entities`、`key_metrics`、`temporal_granularity`、`target_rows`。

**新增一个字段：`analytical_intent`** —— 这份数据被收集来回答什么问题，2–4 条，每条是一个分析动作。

现有的 `data_context` 里其实已经隐含了它（"为了优化高峰调度、识别维护瓶颈"），但它现在是散文，无法被下游消费。改为显式列出。

**它为什么承重**：Phase 3 选图时用它来决定画什么图。

| 分析意图 | 蕴含的视图形态 |
|---|---|
| 识别瓶颈 / 找出表现最差的 | 排序比较 → 条形族 |
| 优化高峰时段 | 时间 × 实体 → 趋势族 / 热力图 |
| 理解构成变化 | 部分与整体随时间 → 构成族 |
| 检验两个指标是否相关 | 双数值 → 关系族 |

这样图表选择有原则可依，而不是在枚举结果里随机截断。同时 **caption 从装饰变成承重结构**——它既是选图的输入，也是一个可选的输出目标（chart-to-text）。

其余部分（一次性 one-shot 示例、场景级 embedding 去重、`target_rows` 按复杂度分层）保持不变。

---

## 3. 为什么仍然不提图表类型

现有 spec 的「chart type isolation」是正确的设计决策，继续保留：Phase 1 不出现任何图表类型词汇。

理由不变——**真实数据源于业务需求，图表只是数据的投影**。过早绑定图表类型会让 LLM 生成被模板挟持的 schema（为了画饼图而生造出恰好三到八个、加起来是 100% 的类别）。

分析意图与图表类型是不同层次的东西：意图说的是「要回答什么问题」，图表类型说的是「用什么形状画」。前者属于业务，后者属于可视化。把选择权留在 [04_figure_selection.md](04_figure_selection.md)。
