# 05 · 渲染

> 新增阶段。现有 pipeline 里渲染是 Phase 3 末尾的一行 `render_chart(view, view_spec)`。

## 1. 为什么重心在这里

数据层的复杂度对最终图像几乎不可见。一张 `AVG(cost)` 的条形图，其数据来自带 per-entity effect 的对数正态分布还是均匀分布，图像与答案完全一致。**图像的多样性完全由渲染层决定。**

现有 pipeline 在数据层投入了大量复杂度（分布族、效应模型、相关结构、三层验证），渲染层只有一行。这个比例与最终任务不匹配——ParseBench 的困难全部落在渲染层能覆盖的范畴内。

同时，风格与数据的分离带来一个真实图表语料结构上无法提供的性质：**ground truth 对风格向量不变**。同一个 FigureSpec 渲染 N 个视觉版本，共享同一份答案，得到配对数据。没有两张真实图表是"同数据不同风格"的。

---

## 2. 八个采样维度

按对 ParseBench 的重要性排序：

| 维度 | 取值范围 | 对应它的哪个困难 | 工作量 |
|---|---|---|---|
| **数值标注** | 全画 / 全不画 / 部分画 | 显式策展划分轴；决定容差是 0 还是 1% | 小 |
| **版面** | 单图 / 网格面板 / 共享轴 / 外置共享图例 / 每面板独立图例 | 多面板共享坐标轴与图例 | 小 |
| **图表族** | 补 compound（同面板 bar + line 双轴） | 其四类图之一 | 小 |
| **数字格式** | 千分位 / 货币符号 / 百分比 / K,M,B 后缀 / 括号负数 | format normalization | 小 |
| **配色** | 企业 BI 低对比 / 同色系 / 渐变填充 / 灰度打印 | custom BI palettes | 中 |
| **渲染后端** | matplotlib / plotly / 企业模板（粗边框、投影、伪三维） | stylized corporate infographics | 中 |
| **图像退化** | JPEG 压缩 / 降采样 / 扫描噪声 / 轻微旋转与透视形变 | low-resolution, scanning artifacts | 中 |
| **页面合成** | 图表嵌入带正文、页眉、页脚、表格的版面 | **整个 Visual Grounding 维度** | 中 |

前四项是渲染器内部参数；后四项需要多后端支持、图像退化管线、以及一个简单的版面排布器。

**数值标注这一维度值得单独说明**：因为渲染完全受控，同一份数据、同一个 FigureSpec 可以渲染两次——画标注与不画标注——ground truth 完全相同。这是配对消融，直接对准 ParseBench 刻意设置的划分轴，且真实图表语料做不出来。

---

## 3. 页面合成：最划算的一项

ParseBench 的图表来自 PDF 页面，其 Visual Grounding 维度的分类标签集是 `{Text, Table, Picture, Page-Header, Page-Footer}`。

如果把图表合成进一张带正文、页眉、页脚、表格的版面，则：

- **页面元素的 bbox 与类别标签完全免费得到**，且标签集与它完全对齐
- 图表定位任务才变得非平凡——直接输出裸图像时图表占满整幅画面，定位是平凡的，训练不出任何东西
- 单页多图、跨栏、图注与图表分离等真实版面现象随之可控地引入

这一项是把 Visual Grounding 维度纳入射程的唯一途径，成本只是一个版面排布器。

## 4. Registry 需要补的部分

现有 [Chart Type Registry](../data_generation/chart_type_registry.md) 定义 6 族 16 型，结构本身保留。需要补的：

- **compound / 双轴**：同一面板内 bar 与 line 混合、左右两个纵轴。ParseBench 四类图之一，现有 registry 完全没有。它引入的困难是真实的——两个纵轴意味着同一像素高度对应两个不同的值。
- **面板级属性**：registry 现在描述的是单张图的结构约束，需要扩展出面板共享关系（共享 x / 共享 y / 共享图例）的表达。

不建议扩的方向：单纯增加图表类型数量。16 型在 2026 年已是基线配置，且不解决任何被测出来的困难。若要扩，方向是非规范图表（流程图、信息图）——那是 ChartArena 测出的真实空白，但属于另一个课题。
