# 样例分析怎么做

设计文档。要回答的是：**这一页用了哪些组件，其中哪些我们的流水线画不出来**——共享图例、双 y 轴、参考线、两级刻度标签这一类。不是抽取数值（数值已有真值）。

---

## 1. 一次调用，整页原图，不做任何预处理

```
page.png（整页 150 dpi） ──► VLM 一次结构化输出 ──► reports/<stem>/
                                                        │
                                    与 chart.jsonl 的标签交叉核对（程序）
```

没有定位步骤，没有裁剪，没有 OCR，没有工具，没有多轮。

### 为什么这样就够：这份组件词表本身就是这么得出来的

[reports/README.md](../reports/README.md) 那 26 项组件词表，是**在 120–130 dpi 的整页渲染上看出来的**，一张图都没有裁过。参考线带独立图例项、两级 x 轴标签、旋转刻度、堆叠与分组同图、零线居中的分叉条、窄分段的数值标签移到外部带引线——全部在整页上可辨。

要检测的组件都是**大尺度结构特征**，不是细小文字。整页足够。

### 裁剪能带来多少，以及为什么不值

按 `2023-05-sigma-01-english_p24` 的 Figure 17 实算（图占页宽 88%、页高 32%）：

| 路径 | 图表在送达图像里占多大 |
|---|---|
| 整页 | 0.62C × 0.32C |
| 裁剪后重渲染 | 1.00C × 0.52C |

`C` 是服务端对长边的缩放上限，两条路径都会触到它，所以比值与 `C` 无关：**线性 1.6 倍，像素 2.6 倍**。

代价是一次额外调用、一个会失败的定位步骤，换 1.6 倍——对大尺度结构判断不划算。

> 更正：前一版写的是「2.7 倍线性」，算错了。正确值 1.6 倍，计算过程如上。

### 为什么不接 OCR

**567/568 页有 PDF 文字层**（`pdftotext` 实测，只有 1 页少于 50 个字符）。需要页面文字时直接取，精确且免费，OCR 只会在本来没有误差的地方引入误差。而且要的不是文字转录，是结构分类。

### 为什么不做 agent

没有需要验证的东西——数值已有 4,864 条真值，不存在"抽出来再设法确认"的循环，而那正是 agent 的主要用途。另外，模型自主决定的多轮调用会让 llmkit 的缓存键不稳定，同一份分析跑两次得到两个结果，48 份报告就无法横向汇总。

### 唯一的回退

结构化输出里留一个 `unreadable` 字段。模型在某一页说"看不清"时，**只对这几页**按框重渲染再问一次。这是异常处理，不是流程的一环。

## 2. 试过但没采用：从矢量内容确定性地框图表

这些 PDF 是矢量的，本可以用 PyMuPDF 的绘图对象做邻近聚类得到图表框。四张测试页：

| 页 | 结果 |
|---|---|
| `2023-05-sigma-01-english_p24` | 正确，两簇分别对应 Figure 16 与 Figure 17 |
| `..._p101` | 正确，一簇覆盖 6 面板图块 |
| `05021ff2-en_p19` | 全页只有 13 个绘图对象，聚不出来 |
| `She-figures_p115` | 0 个绘图对象——这页图表是**嵌入的位图** |

2/4。既然主路径已经不需要图表框，这条记录在此备查，不实现。

## 3. 分析多少页：48，随机

`tools/sample_pages.py`，**均匀随机**抽样，种子 20260817，结果在 `data/stats/analysis_sample.json`。实得 48 页 / 34 份文档 / 覆盖 397 条抽查点。

不做分层、不设每文档上限。理由是汇总表要的是**频次**——[reports/INDEX.md](../reports/README.md#indexmd) 按「我们无」的出现频次排序，那张表直接就是改造顺序。均匀随机的频次是总体频次的无偏估计；任何筛选策略都会让这张表失去这个性质。

抽中的分组构成只报告、不干预：

| 分组 | 抽中 / 总体 |
|---|---|
| `untagged`（数值全写出） | 19 / 188 |
| `need_estimate` | 26 / 309 |
| `3d_chart+need_estimate` | 2 / 68 |
| `3d_chart` | 1 / 3 |

> 前一版做了按分组比例分配 + 每文档 ≤2 页。改回均匀随机：那套策略的目的是"多发现不同组件"，但它与汇总表的频次用途相互矛盾。要覆盖更多，加大 `--size` 即可。

## 4. 不跑全量评测

前一版把「568 页跑一遍 parse 并打分」列进了近期任务。**取消。** 它和样例分析回答的不是一个问题：

| | 回答什么 | 什么时候需要 |
|---|---|---|
| 样例分析（48 页） | 我们缺哪些组件、难点在哪 | **现在**，它决定流水线改什么 |
| 全量 parse + 打分（568 页） | 我们在这个基准上得几分 | 改造完成后，作为改动前后的对照 |

失败案例由人工提供（[data/failure_cases/](../data/failure_cases/)），不需要先跑全量去筛。全量跑挪到 [README](../README.md#todo) 的 D 组。

## 5. 第三条信号是免费的

`chart.jsonl` 的标签本身携带结构证据，不用调模型：

```
labels 有 3 个                        → 三键索引（面板 × 类目 × 系列）
同一页多条规则的首个标签取值重复且少   → 那一维很可能是面板名
labels 里出现 '2022:06' '1Q-2024'     → 时间刻度的格式
```

用它交叉核对 VLM 的输出：模型说"单面板"但规则要三个键，就是矛盾，标进报告。这一步是程序，不是模型。

---

## 6. 代码与产物都在 parsebench 下

只有 `src/llmkit` 从目录外引入（共享的模型调用层，[图像通路已实现](../../src/llmkit/types.py)）。

| 路径 | 内容 |
|---|---|
| `tools/sample_pages.py` | 随机抽样（已实现） |
| `tools/analyze_pages.py` | 一次调用出结构化输出，走 `llm.map()` 并发 |
| `data/stats/analysis_sample.json` | 抽样结果（已产出） |
| `reports/<stem>/` | 一页一份报告，格式见 [reports/README.md](../reports/README.md) |
| `reports/INDEX.md` | 48 份的汇总：组件频次、新组件、难点分布 |

---

## 7. 成本

48 次调用，整页约 2.5k 输入 token、输出约 1k。合计约 **0.12M 输入 + 0.05M 输出**。缓存命中后重跑为零。

---

## 8. 什么时候才需要工具与多轮

刷榜阶段。那时目标是把分拉高，裁剪放大、多轮自检、代码计算都可能有用——CharTool（`2604.02794`）用图像裁剪 + 代码计算在 CharXiv-R 上报告 +8.0%。

但**分析阶段不要提前把系统做成 agent**：分析要测的量之一就是「稠密页面是不是更容易失败」（[04 G5](04_pipeline_gap.md#g5--稠密度上限抬高把稠密度变成一个可控自变量)），给分析器加自适应放大会把这个信号抹掉。
