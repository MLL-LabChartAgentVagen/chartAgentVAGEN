# 样例分析怎么做

设计文档。要回答的是：**这一页难在哪，它用了哪些组件，其中哪些我们的流水线画不出来**——共享图例、双 y 轴、参考线、两级刻度标签这一类。不是抽取数值（数值已有真值）。

---

## 1. 需要多复杂的系统

结论：**两段式固定流程，中间夹一次确定性重渲染。不做 agent，不接 OCR。**

```
page.pdf ──pdftoppm 150dpi──► page.png
                                 │
              ① VLM 定位：这页有几张图，各自的粗框（归一化坐标）
                                 │
              ②' pdftoppm 按框重渲染，350 dpi，四周留 5% 余量   ← 确定性程序
                                 │
              ② VLM 分析：组件清单 + 结构 + 难点（每张图一次）
                                 │
              ③ 与 chart.jsonl 的标签交叉核对                  ← 确定性程序
```

### 为什么不接 OCR

**567/568 页有 PDF 文字层**（`pdftotext` 实测，只有 1 页少于 50 个字符）。需要页面文字时 `pdftotext` 直接给出精确结果，OCR 只会在本来没有误差的地方引入误差。而且我们要的不是文字转录，是结构分类。

### 为什么要裁剪，以及裁剪的价值不在"裁"

A4 页面 150 dpi 是 1240×1754，服务端把长边压到 1568（0.89×），基本不损失。一张占页面 28% 面积的图，送达时约 520×430 px，刻度文字约 8 px 高——判断"是不是双 y 轴""图例是不是跨面板共享"处在边缘。

**同一份像素裁出来没有任何增益。** 增益来自这些 PDF 是矢量的：按框**重新渲染**到 350 dpi，同一张图变成约 1200×1000 px，线性分辨率 2.7 倍。`pdftoppm -r 350 -x -y -W -H` 一条命令，不需要新依赖。

### 图表框从哪来

试过从 PDF 矢量内容确定性地聚类出图表区域（PyMuPDF `get_drawings()` + 邻近并查集）。四张测试页的结果：

| 页 | 结果 |
|---|---|
| `2023-05-sigma-01-english_p24` | 正确，两个簇分别对应 Figure 16 与 Figure 17 |
| `..._p101` | 正确，一个簇覆盖 6 面板图块 |
| `05021ff2-en_p19` | 全页只有 13 个绘图对象，聚不出来 |
| `She-figures_p115` | 0 个绘图对象——这页的图表是**嵌入的位图** |

**2/4，不能作主路径。** 所以框由 ① 的 VLM 给，并且四周留 5% 余量再裁——这一步只要求"框住图块"，比 ParseBench Visual Grounding 的元素级定位（纯 VLM 6–7%）粗一个量级，且框偏一点由余量吸收。矢量聚类可作为交叉验证，不作依赖。

### 为什么不做 agent

「agentic」指模型自己决定调什么工具、调几轮。这里不需要，两条理由：

1. **没有需要验证的东西。** 数值已有 4,864 条真值。分析要的是组件与难点判断，不存在"抽出来再想办法确认"的循环——而这正是 agent 的主要用途。
2. **确定性。** llmkit 的磁盘缓存让 `(prompt, image, model) → 输出` 可复现；模型自主决定的多轮调用缓存键不稳定，同一份分析跑两次得到两个结果，48 份报告就无法横向汇总。

上面的 ①→②' →② 是**固定控制流**，每一步的输入由上一步确定性地决定，不是 agent。

## 2. 分析多少页

**48 页，不是 568。** 分层随机抽样，`tools/sample_pages.py`，结果在 `data/stats/analysis_sample.json`。

| 层 | 抽样 / 总体 |
|---|---|
| `untagged`（数值全写出） | 16 / 188 |
| `need_estimate` | 25 / 309 |
| `3d_chart+need_estimate` | 6 / 68 |
| `3d_chart` | 1 / 3 |

按层比例分配，最小配额 1（否则 3 页的层会被抽没）；**每份源文档最多 2 页**——99 份文档里 `ac8b3538-en` 一份占 52 页，均匀抽样会主要在描述这一份文档的模板。实得 48 页 / 36 文档 / 覆盖 413 条抽查点。种子固定为 20260817。

组件清单是有限词表（见 [reports/README.md](../reports/README.md)），48 页足以把常见组件覆盖到；出现频次的精确估计不是这一步的目的。

## 3. 不跑全量评测

前一版把「568 页跑一遍 parse 并打分」列进了近期任务。**取消。** 它和样例分析回答的不是一个问题：

| | 回答什么 | 什么时候需要 |
|---|---|---|
| 样例分析（48 页） | 我们缺哪些组件、难点在哪 | **现在**，它决定流水线改什么 |
| 全量 parse + 打分（568 页） | 我们在这个基准上得几分 | 改造完成后，作为「改动前后」的对照 |

失败案例由人工提供（[data/failure_cases/](../data/failure_cases/)），不需要先跑全量去筛。全量跑挪到 [README](../README.md#todo) 的 D 组。

## 4. 第三条信号是免费的

`chart.jsonl` 的标签本身携带结构证据，不用调模型：

```
labels 有 3 个                        → 三键索引（面板 × 类目 × 系列）
同一页多条规则的首个标签取值重复且少   → 那一维很可能是面板名
labels 里出现 '2022:06' '1Q-2024'     → 时间刻度的格式
```

用它交叉核对 ② 的输出：VLM 说"单面板"但规则要三个键，就是矛盾，标进报告。这一步是程序，不是模型。

---

## 5. 代码与产物都在 parsebench 下

只有 `src/llmkit` 从目录外引入（它是共享的模型调用层，[图像通路已实现](../../src/llmkit/types.py)）。其余代码、中间产物、报告全部在 `parsebench/` 内：

| 路径 | 内容 |
|---|---|
| `tools/sample_pages.py` | 分层抽样（已实现） |
| `tools/analyze_pages.py` | ①→②' →②→③ 四步，走 `llm.json(..., images=[...])` 与 `llm.map()` |
| `data/stats/analysis_sample.json` | 抽样结果（已产出） |
| `reports/<stem>/` | 一页一份报告，格式见 [reports/README.md](../reports/README.md) |
| `reports/INDEX.md` | 48 份报告的汇总：组件频次、缺口排名 |

---

## 6. 成本

48 页 × 1 次定位 + 约 70 张图 × 1 次分析 ≈ 120 次调用。整页约 2.5k 输入 token，350 dpi 的裁剪图约 1.5k。合计约 **0.3M 输入 token**，缓存命中后重跑为零。

---

## 7. 什么时候才需要工具与多轮

刷榜阶段。那时目标是把分拉高，裁剪放大、多轮自检、代码计算都可能有用——CharTool（`2604.02794`）用图像裁剪 + 代码计算在 CharXiv-R 上报告 +8.0%。

但**分析阶段不要提前把系统做成 agent**：分析要测的量之一就是「稠密页面是不是更容易失败」（[04 G5](04_pipeline_gap.md#g5--稠密度上限抬高把稠密度变成一个可控自变量)），给分析器加自适应放大会把这个信号抹掉。
