Record it while drawing
At the moment a mark is drawn, the box, the key and the value are all in hand at once. Parsing a finished image has to recover that correspondence, and that recovery is the error being removed.
Annotate afterwards
Human reads the value, human draws the box, someone aligns them. Cost per pair, and error at every step.
Record at draw time
The renderer already computed the pixel position from the value. Write both down. Cost zero, error zero.

Why not two calls

The script is the formalized scenario. Splitting them inserts a layer that loses exactly what the downstream needs.

Call 1 writes prose, call 2 recovers columns
entities: ["Mercy General", "St. Luke's", "Riverside",
 "Internal", "Surgery", "Pediatrics", "Trauma",
 "mild", "moderate", "severe"]
Ten strings in one flat list. That hospital contains department, and that mild < moderate < severe, are not in there. The second call invents both.
And intents were written before the columns existed, so they get re-bound by inference too.
One call writes both
dim("department", [...], parent="hospital")
dim("severity", [...], ordered="ordinal")
Hierarchy, orderedness, unit and additivity are declared fields. The intent points at a column that is being defined in the same file.
Binding holds by construction. Nothing to infer.
There was also no way back. Stage 2 could not tell stage 1 that a declared metric was unimplementable — the pipeline is one-way, so that failure degraded the output silently.

The model writes a program, not numbers

Four declaration methods. Columns are declared first, rows are emitted last.

# dimension group: entity, hierarchical dim("hospital", ["Mercy General", "St. Luke's", "Riverside"], weights=[.40, .35, .25]) dim("department", ["Internal", "Surgery", "Pediatrics", "Trauma"], parent="hospital", weights={"Mercy General": [.35, .25, .15, .25], ...}) # dimension group: triage, ordered but not a process stage dim("severity", ["mild", "moderate", "severe"], weights=[.50, .35, .15], ordered="ordinal") time("visit_date", start="2024-01-01", end="2024-06-30", freq="daily") # dow / month / quarter / weekend derived # measures are expressions. Dependencies are read off the free variables. measure("wait_minutes", "lognormal(mu = 2.8 + 0.4*[severity=moderate] + 0.9*[severity=severe]" " + 0.2*[hospital=Mercy General], sigma = 0.35)", unit="min", additive=True) measure("cost", "wait_minutes * 12 + {mild:80, moderate:260, severe:700}[severity]" " + gaussian(0, 30)", unit="CNY", additive=True) measure("satisfaction", "clip(5.2 - wait_minutes / 32 + gaussian(0, 0.3), 1, 5)", unit="score", additive=False) emit(900)

Which charts are drawable is known before any row exists

Cardinality comes from the value lists. Additivity and orderedness are declared fields. No data is needed.

Families, not a candidate list

02 Three kinds of figure, three mechanisms

No model call here. Only one of the three needs a random number.

Intent figure · constructed
hospital × AVG(wait), comparison
→ bar( hospital, AVG wait )
The binding fixes the columns, the aggregate and the family. The condition table picks the type. Nothing is searched.
Multi-panel · derived
anchor + drill-down rule
→ grouped_bar( hospital × dept )
The second panel is computed from the anchor by the relationship rule. Nothing is searched.
Rotation · sampled
draw (type, columns, aggregate)
→ test → keep or redraw
No target is specified. The ask is "another one that is not a repeat", which is what sampling is for.
What this replaces
Enumerating every legal view, projecting all of them, then picking a few. That is a few hundred candidates on this schema and a few thousand on a wide one — each needing a full pass over the table.
What it costs now
This run drew 14 candidates and kept 3. Intent and multi-panel figures are built directly, so they cost one projection each.
All figures come off one fact table, so cross-chart consistency holds by construction.

Diversity is a test, not a count

Capping the number of figures does not stop them from being near-copies of each other.

A count cannot see this
bar( hospital, AVG wait )
bar( hospital, SUM wait )
bar( hospital, AVG cost )
bar( hospital, COUNT(*) )
Four figures, same three labels, same three boxes. Only the heights move. A budget of 8 admits all of them.
Admission test
Reject a candidate when the batch already holds a figure with the same key set and the same mark shape.
bar( hospital, SUM cost ) → reject
pie( hospital, SUM wait ) → keep sector, not rect
box( department, wait )  → keep different keys
No threshold to tune.
Why that pair
The output unit is (key, value, region). The key set decides which entities appear; the mark shape decides what the box looks like, how many values it carries, and whether the value is readable at all.
K is only a budget
Render and storage cost, nothing else. How many figures a scenario actually yields falls out of the test and of running dry.
Multi-panel figures are exempt — their value is the layout form, and the repeated keys are exactly what makes them a paired sample.

The anchor must already be a standalone figure
Then that view appears twice — alone and as panel p0 — with identical keys and values and different pixels. Sample the anchor independently and that pair disappears.

Three checks on the production path

Record-while-drawing rests on the plotting library's internal transform. When that is wrong nothing throws — it quietly emits a shifted box.

Is anything in the box
Read the rendered PNG back, take the pixels inside the box, check the mark's own colour occupies enough of them.
[168,196,278,520] → 96% blue
catches a shifted axes rect, a dpi mismatch
Does the geometry match the value
Invert the box through the panel's value range and pixel range, compare to the recorded value.
(520 − 196) × 0.13 = 42.1  vs  42.3
catches log axes, negative values, stacked baselines
Does the answer survive a restyle
The two style versions of one FigureSpec must carry an identical key-to-value map.
42.3 / 35.8 / 28.1  both times
catches a style parameter leaking into the data
Not a test suite
These run on every figure in production. A fixed sample in a unit test cannot reach the failure — it only shows up on real data.
The third one is free
Style-paired renders are already a product of the pipeline. The check reads the pair that ablation needs anyway. Render once, use twice.

The claim, and how it fails

Grounded transcription can be done by a single VLM — extracting every value together with the region it was read from — matching dedicated parsers on chart-to-table while reaching layout-pipeline-level visual grounding.
Why the data can only be generated
Value-and-region pairs at scale cannot be annotated onto real charts. A human reads the value, a human draws the box, and someone has to align the two. Recording at draw time makes it exact and free.
Failure criterion
Add the region to the output and numeric accuracy falls below the table-only control. Then the claim does not hold, and no other result rescues it.
Also pre-registered: turning off L2 with no change in grounding demotes atomic grain to an implementation detail.

Five invariants

What holds at every stage

Atomic grain
One fact-table row is one indivisible event. Aggregation happens only in the stage 2 projection.
The model never produces a number
One call, and it writes a script and a set of bindings. Every value comes from the engine.
Define, never select
Feasibility, pairing, layout and figure choice are all table lookups, so type coverage is a rotation rule rather than a model preference.
Annotation is free and exact
Every ground truth value is written out of renderer state. Nothing is estimated, nothing is labeled by hand.
Style carries no truth
Ground truth follows the FigureSpec. N appearances, one answer — which is what makes the style ablation possible at all.
